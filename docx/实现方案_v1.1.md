# 1. 框架分层总览（不变，补充映射）

Framework → Gameplay → Presentation → UI 四层不变。补充与 GF（Game Framework）的模块对应关系，便于对照学习：

| 本项目 | GF 对应 | 说明 |
|---|---|---|
| EventBus | Event 模块 | 我们已事件化；v1.1 补 Fire/FireNow 双路径语义 |
| SimplePool | ObjectPool 模块 | 简单版够用；v1.1 定增强路线 |
| GameFlow | Procedure 模块 | v1.1 升级：全局流程阶段化 |
| （无） | Entity 模块 | 遭遇导演（M4）引入实体编号思想 |
| UIManager+BasePanel | UI 模块 | v1.1 直接采用 UIGroup/打开序号/三段生命周期 |
| AudioManager（M2 新建） | Sound 模块 | v1.1 直接采用分组+代理+序号方案 |
| SaveSystem（M2 新建） | Config/Setting/FileSystem | v1.1 采用三分法：内容配置/用户偏好/进度存档 |
| 调试控制台（M4） | Debugger 模块 | v1.1 采用窗口+业务计数注入 |

明确不引入的（学习后决定）：DOTS/ECS（怪物量级不足，手写Driver+FSM足够；但"高频开关用状态字段而非增删组件"的原则吸收）、Resource 热更（单机无此需求）、Localization/WebRequest/Download/FileSystem（暂不，存档直接 JSON 落盘）。

# 2. 技术篇整合清单（v1.1 核心新增）

每条：篇目 → 启示 → 落到哪里。★ = 直接写入后续系统设计。

## 2.1 架构与流程

| 篇目 | 启示 | 落地 |
|---|---|---|
| ① 整体架构与启动 ★ | 三层分工：核心/适配/业务。每帧由统一入口调度模块（Priority 排序），不为每个管理器挂 MonoBehaviour | GameFlow 升级时把全局 Update 收敛；新管理器类优先纯 C# + 单一驱动入口 |
| ② FSM ★ | FsmState<TOwner>：OnInit(注册时一次)/OnEnter/OnLeave/OnUpdate；切换条件写在状态内部（ChangeState<T>）；Owner 存数据、状态存行为；状态实例每角色一份 | **M3 怪物通用 FSM 的直接蓝本**。当前 MonsterBrain 的 if 链（索敌/追击/攻击/僵直/死亡）→ 拆成 Idle/Chase/Attack/Stagger/Dead 五个状态类，MonsterBrain 退化为 Owner（数据+感知） |
| ③ Procedure ★ | 全局阶段=状态机：Launch → Camp（整备菜单）→ Encounter（战斗）→ Settlement；流程自己持有完成条件（configReady && sceneReady 收齐才推进）；流程间数据用键值传递；入口流程从配置启动 | **GameFlow v2 设计**：现有 GameFlow（团灭判定+R重开）升级为 Procedure 制，为营地系统（M2后段）和遭遇导演（M4）铺路 |
| ⑩ Entity | 实体=编号+资源+逻辑三分；OnInit 缓存组件、OnShow 收本次数据、OnHide 结束本次行为；隐藏≠销毁（组内池复用，不依赖 Start 重跑） | M4 遭遇导演生成怪物用"编号+数据包"模式，替代现在 WaveSpawner 直接 Instantiate |
| ⑨ Scene / ㉓ 模块协作 ★ | 异步任务"完成"由事件/回调判定，不是代码执行到下一行；流程切换前收齐全部依赖条件；退出按所有权清理（自己创建的自己清，不清全局） | 写进代码规范第 7 条：发起异步加载必须订阅成功事件后才推进状态 |

## 2.2 事件与对象管理

| 篇目 | 启示 | 落地 |
|---|---|---|
| ④ Event ★ | 双路径：Fire（入队，帧末分发，防嵌套失控）vs FireNow（立即同步，适合必须即时场景）；事件对象分发完即回收，订阅者只在使用期间读取（需要久存先拷贝） | EventBus 补队列语义：DamageDealtEvent 量大时改 Fire 队列分发；文档注明"订阅回调里不长期持有事件参数" |
| ⑤ ReferencePool | 池化 C# 对象必须 Clear 断开引用（防池长期持有业务对象） | 现有 _hitIds/_tipPts 等 HashSet/List 复用时注意 Clear；DamageInfo 是 struct 天然免池 |
| ⑥ ObjectPool ★ | 三态：Spawn（借用）/Unspawn（归还，实例保留）/Release（最终销毁）；容量与过期策略只作用于空闲对象，不杀使用中实例 | SimplePool 增强路线（M2 顺手做）：①归还≠销毁已有；②加容量上限+过期清理；③飘字/特效入池（原计划 P2 项，提前） |

## 2.3 UI 与音频（M2 的直接设计依据）

| 篇目 | 启示 | 落地 |
|---|---|---|
| ⑪ UI ★★ | ①UIGroup 分层：HUD / Window（互斥覆盖）/ Popup（置顶）；②打开返回序号，按序号关闭本次打开；③Covered（被覆盖）≠Paused（被暂停）两语义；④生命周期三段：OnInit(缓存引用) / OnOpen(收本次参数) / OnClose(解绑本次订阅)；⑤关闭≠销毁，实例可复用，不能依赖 Awake/Start 重跑 | **BasePanel 设计定稿**（替换 v1.0 模糊条目）：抽象类 BasePanel{OnInit/OnOpen(userData)/OnClose}；UIManager 持组+序号；现有 InventoryUI/ChestPanel 迁入。M2 第一项做 |
| ⑫ Sound ★★ | ①SoundGroup 分组（BGM/UI/战斗音效），组内独立音量；②SoundAgent 代理池限并发（代理不足按优先级替换）；③播放返回序号，按序号 Stop（带淡出）；④谁发起谁持有序号、谁负责停；⑤循环音/一次性音分开策略 | **AudioManager 设计定稿**（M2）：AudioManager(组件)+SoundGroup(纯C#)+代理 AudioSource 池。接 EventBus：DamageDealtEvent→命中音、UnitDiedEvent→死亡音、PickupEvent→拾取音（拾取事件化一并做） |

## 2.4 数据与配置

| 篇目 | 启示 | 落地 |
|---|---|---|
| ⑬ Config + ⑯ Setting ★ | 三分法：内容配置（Config/DataTable，随版本）/ 用户偏好（Setting：音量、画质，Set≠Save，拖滑杆实时改、确认才落盘）/ 运行时数据（DataNode，易失） | **存档与设置设计定稿**（M2）：GameData 拆分——内容数值留 SO；玩家偏好（音量等）走 PlayerPrefs 封装；进度存档（金币/等级/背包/迷雾）走 SaveSystem JSON+版本号。设置界面拖音量=实时改 AudioMixer 值，松开/关闭面板才 Save |
| ⑭ DataTable | 大量记录用 Id 关联（关卡→掉落→物品），导出期校验重复 Id | 与 SO 资产等价，新增：掉落表/波次表建 SO 时加 OnValidate 查重 |
| ⑮ DataNode | 少量跨模块运行状态可用路径树；数据改变不自动通知 UI（存取与通知是两件事，先改数据再发事件） | 不引入 DataNode（事件已覆盖）；原则吸收："写数据→发事件"顺序写进规范 |

## 2.6 ECS 系列（4篇）——不引入，吸收一条原则

不用 DOTS 的理由不变（怪物量级、开发成本）。吸收：*数值变化改字段，高频开关用状态字段/Enableable 思想，只有"真正获得长期能力"才动结构*。映射：僵直/缴械用计时字段，不加删组件；未来 Buff 系统用状态字段列表而非动态组件增删。

# 5. 代码规范增补（第 4 条后追加）

7. 异步任务（加载/场景/下载）的"完成"只认事件/回调，禁止"执行到下一行就当成功"；流程推进前收齐全部依赖条件
8. 事件订阅回调不得长期持有事件参数；需要久存的数据先拷贝
9. 关闭≠销毁：所有可被复用的对象（UI 实例/实体/音效代理）按"借用-归还"管理，本次使用的订阅在关闭时解绑
10. 写数据→发事件的顺序固定，先改状态再通知
