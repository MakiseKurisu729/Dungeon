# ADR-0001 — 事实与规划分离

- 状态：`Accepted`
- 日期：2026-11-03
- 决策者：用户（产品决策），K3.1（架构收敛），OpenCode＋DeepSeek（文档落地）

## 背景

仓库长期只有一份根目录 `AGENTS.md` 自称"唯一真相源"，同时承载架构规则、目录说明、历史进度和踩坑记录。设计文档（01～05）描述的是目标状态，旧聊天与归档文档描述的是过去状态，而"当前实际能用什么"没有任何单一来源。结果是：设计目标容易被当成已完成能力，历史进度容易被当成当前事实。

## 决策

把项目知识按性质拆开记录，各自只承担一种职责：

| 类别 | 存放位置 | 允许的内容 |
|---|---|---|
| 事实基线 | `Docs/00_项目事实基线.md` | 已核验事实；明确标注为"待复验"的用户报告 |
| 目标设计 | `Docs/01`～`05` | 架构、计划、规范、清单（目标状态） |
| 历史决策 | `Docs/Decisions/` | 已接受的 ADR，不改写历史 |
| 待验证项 | `Docs/QA/` + 行为矩阵 | 真实验收结果与证据 |
| 历史资料 | `Docs/Archive/` | 仅追溯，不作为开工依据 |

并规定文档效力顺序：

1. 当前任务书与硬约束
2. 当前事实基线
3. 已批准的架构和 ADR
4. 仓库实际行为
5. 历史文档与聊天记录

## 原因

- 避免把设计目标或聊天描述误写为已完成能力。
- 避免新会话在没有上下文的情况下把旧进度当现状继续开发。
- 让"是否可用"这个问题只有一个回答入口，且该入口的每条结论都能追溯到来源。

## 后果

**正面**

- 任何"已实现"的判断都必须先经过 Unity 复验并留下 QA 记录。
- 规划变更不会污染事实基线；事实更新也不会被误读为设计变更。
- 归档文档可以保留，但不会被当作开工依据。

**代价**

- 维护成本上升：同一功能可能同时出现在设计文档、事实基线和 QA 记录中，需要保持状态同步。
- 需要人工纪律：用户报告在复验前必须停留在"待复验"状态。

## 备选方案与被否决原因

- **继续维护单一 `AGENTS.md`**：无法区分目标与现状，历史上已经导致误判，否决。
- **只保留设计文档**：设计文档天然描述目标，不能回答"现在能不能用"，否决。
