# ADR-0002 — 当前 AI 协作路由

- 状态：`Accepted`
- 日期：2026-11-03
- 决策者：用户（产品决策）

## 背景

项目同时使用多个 AI 入口（规划型与本地执行型）。若不明确分工，容易出现：规划方直接改代码、执行方自行扩大范围、或无人对"是否真的通过验收"负责。

## 决策

确立三层协作路由：

| 角色 | 职责 | 不负责 |
|---|---|---|
| 用户 | 产品决策、Unity 集成与验收、提交和远端推送 | 逐行实现 |
| K3.1 | 事实校准、架构收敛、工单编写、独立审查、文档维护 | 本地批量改代码、代替用户验收 |
| OpenCode＋DeepSeek | 按任务包执行本地受控任务 | 自行扩大范围、自行提交/推送、自行判定 Done |

配套规则：

- 任务状态只有用户能最终确认为 `Done`。
- AI 不执行 `git commit` / `git push` / 发布 / 删除分支。
- 执行方遇到"仓库与任务基线不符"必须停止并报告，而不是自行修正基线。

## 原因

- 把"规划—执行—验收"分开，能让独立审查真正独立。
- 用户是唯一同时掌握产品意图与 Unity 实际运行结果的人，验收权必须集中。
- 执行方权限收窄后，任务包的边界描述才有意义。

## 后果

**正面**

- 每类角色有明确交付物：任务包 / 代码改动 / 验收记录。
- 争议可以回到"文档效力顺序"裁决。

**代价**

- 一人公司式的低延迟不再存在，每个任务至少多一次交接。
- 任务包质量成为瓶颈：任务包写不清，执行就会跑偏。

## 变更方式

本路由**不是永久架构**。将来如需调整，应新建 `ADR-000N` 说明新路由并标注本 ADR 为 `Superseded by ADR-000N`。

**不得**直接修改本文件内容来冒充新决策，也不得删除本记录。
