# 规范 — spec 层与本项目产物的映射

本目录对应《Spec-Driven Development with Coding Agents》的 spec 层。**不新增第二份真相**：硬约束看 `AGENTS.md`，模板与格式看 `Docs/交接/工作流规则.md`。

## 文件

| 文件 | 作用 | 更新时机 |
|---|---|---|
| `项目宪法.md` | 三根柱子：Mission / Scope / Tech stack，另索引 Roadmap 与不变量 | 仅 Replanning |
| `规范说明.md` | 本文件：映射与用法 | 目录结构变化时 |

## 课程产物 → 本项目产物

| 课程产物 | 本项目产物 | 说明 |
|---|---|---|
| `项目宪法.md` | `Docs/规范/项目宪法.md` | 1 页索引，不复制 `00`/`01`/`02` |
| `specs/<feature>/requirements.md` | `Docs/交接/TASK_<ID>_<中文>.md` **§1 需求** | 合并进同一文件，避免三份重复维护 |
| `specs/<feature>/plan.md` | 同文件 **§2 方案** | 至少 A/B 两案 + 取舍 |
| `specs/<feature>/validation.md` | 同文件 **§3 验证**（AC 表） | 断言 ID + 证据路径，强于人工 review |
| implement | 执行者按 TASK 改代码 | 见 `AGENTS.md` §3 |
| validate | 大脑按 AC 表复审 | 见 `.opencode/skills/acceptance-loop/` |
| learn | `Docs/学习/<ID>_讲稿.md` | AI 写完整稿 + 所有者按需批注 |
| replan | `Docs/交接/工作流规则.md` §9 清单 | 10 分钟收口，单独提交 |

## 为什么合并三份文件

课程按 feature 拆 `requirements / plan / validation` 三个文件，是为了跨会话、跨人评审。本项目是“大脑写 TASK → 执行者一次执行 → 用户验收”的单线流转，拆三份只会产生同步成本与版本漂移。因此固定为**一个 TASK 三节**，节名与课程一致（需求 / 方案 / 验证），便于对照讲解。

## 用法

1. **开新 feature**：加载 `feature-spec` skill，套 `Docs/交接/任务模板.md` 写三节（含 AC 表）。
2. **所有者审 spec**：只审三处 —— §1 需求是否可验收、§2 方案取舍是否成立、§3 AC 是否覆盖边界。
3. **收口**：加载 `replan` skill，按 `Docs/交接/工作流规则.md` §9 走 10 分钟清单。
