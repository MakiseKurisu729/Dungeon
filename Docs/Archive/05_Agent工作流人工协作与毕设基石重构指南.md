# 魔石地牢：Agent 工作流人工协作与毕设基石重构指南

> 文档版本：v1.0  
> 编制日期：2026-11-02  
> 当前目标：先把现有工程重构成可持续开发、可验证、可用编辑器工具辅助生产的“毕设基石”，再开始三层地牢、职业扩充、完整首领和联机内容。  
> 当前工具路由：**K3.1 Pro 负责规划、架构收敛、工单和独立审查；OpenCode＋DeepSeek 负责本地编码；用户负责产品决策、关键差异审查、Unity 集成和最终验收。**  
> 文档关系：本文是当前阶段的操作手册；通用架构、任务包和防回退规则继续参照文档 01、03、04。若工具路由与旧文档不同，以本文当前配置为准。

## 0. 一句话工作原则

**AI 可以写大部分实现，但用户必须知道它为什么这样写、实际改了什么、如何证明正确，以及什么时候拒绝继续执行。**

本阶段不追求“让 AI 自动做完整个游戏”，而追求：

1. 每个变更都有边界、有证据、可回退；
2. 新职业、新敌人、新交互、新楼层不再需要修改所有核心系统；
3. 重复、确定性的编辑器操作逐渐由工具完成；
4. 用户的主要精力从复制脚本和机械点击，转向玩法选择、结构判断、运行验收和内容集成。

## 1. 对过去开发方式的校正

过去“讨论构想 → 生成目录和步骤 → 粘贴脚本 → 运行 → 描述问题 → 替换脚本”的流程适合早期试验，但存在六个根本问题：

1. **目录不等于架构。** 架构必须说明职责、状态归属、调用关系和依赖方向。
2. **能运行不等于正确。** 编译和单次运行不能覆盖死亡、取消、切场景、重复交互、对象回收等边界。
3. **整脚本替换容易扩大回归。** 后续默认局部差异修改，不允许把重写当作通用修复手段。
4. **自然语言现象不足以定位。** 必须补充复现步骤、预期、实际、日志和对象状态。
5. **实现者不能自己宣布验收。** 完成声明必须由差异、测试和 Unity 实际结果支持。
6. **人工不应长期承担重复编辑器操作。** 能确定规则的操作应逐步沉淀为可复查工具。

当前仓库中的技能具体类耦合、Boss 职责混合、多个系统全场扫描和交互直读输入/UI，不只是“没有审查”的结果，更是过去允许每次实现都走局部最短路径的结果。本阶段必须改变任务生成方式，而不只是增加一个审查提示词。

## 2. 当前角色分工

| 角色 | 当前承担者 | 必须完成 | 不得代替别人完成 |
|---|---|---|---|
| 产品负责人 | 用户 | 决定目标体验、优先级、砍 scope、选择方案 | 不把“是否值得做”全部交给模型 |
| 技术负责人 | K3.1 Pro＋用户审批 | 维护事实基线、架构边界、ADR、任务拆分和验收条件 | 不凭空猜仓库现状；不把规划写成已实现 |
| 编码执行者 | OpenCode＋DeepSeek Flash | 在本地分支按工单修改代码、编写最小测试、报告真实结果 | 不全仓漫游、不自由重构、不安装新包、不推送远端 |
| 疑难执行者 | DeepSeek Pro，按需 | 处理已经缩小范围的复杂问题 | 不作为所有任务的默认模型 |
| 独立审查者 | K3.1 Pro 独立会话，或其他不同模型 | 只根据工单、契约、diff 和测试证据找问题 | 不沿用实现者结论，不重新设计整个系统 |
| Unity 集成与 QA | 用户 | 编译、PlayMode、预制体/场景/动画检查、玩法体验、验收 | 不把“打开没报错”当作完整验收 |
| 提交与发布负责人 | 用户 | 确认本地提交、远端推送和版本发布 | AI 不自行推送、发布或删除分支 |

### 2.1 K3.1 Pro 的输入与输出

K3.1 Pro 不需要每次阅读整个项目。规划时优先提供：

- 当前事实基线；
- 本阶段目标和非目标；
- 相关架构章节；
- 当前模块的关键代码或调用关系；
- 上次验收和遗留问题；
- 用户希望改变的实际开发痛点。

它必须输出可执行工单，而不是泛泛建议。信息不足时，只能列出最小补充材料，不得编造现状。

### 2.2 DeepSeek 的输入与输出

DeepSeek 默认只接收：

- 简短的 `AGENTS.md`；
- 当前工单；
- 工单列出的相关文件；
- 必须遵守的 1～2 段架构约束；
- 必要日志和测试命令。

它必须返回：

- 最小修改计划；
- 实际修改文件；
- 真实测试结果和未运行项目；
- 编辑器影响；
- 已知风险与遗留问题。

### 2.3 用户不再承担的工作

以下不再作为默认人工流程：

- 在聊天和 IDE 之间逐段复制脚本；
- 不看差异就覆盖整个文件；
- 每个任务重复进行同样的组件挂载和字段设置；
- 只凭“感觉不对”让 AI 反复重写；
- 为了完成一个小功能接受全项目整理。

## 3. 用户必须亲自完成的六类工作

### 3.1 决定做什么、不做什么

每次开发前，用户必须能用一句话说明本轮结果，例如：

> 本轮回合结束后，单位生成和销毁会被统一注册，其他行为保持不变。

以下表述不能直接开工：

- 优化架构；
- 完善战斗；
- 做好职业系统；
- 提高扩展性；
- 修复所有问题。

### 3.2 审批系统边界

新系统或重构前，至少确认：

1. 它负责什么、不负责什么；
2. 输入和输出是什么；
3. 核心状态由谁拥有；
4. 允许依赖谁，禁止依赖谁；
5. 对象生成、销毁、回收和切场景时如何清理；
6. 如何验证旧行为没有改变。

### 3.3 审查关键差异

不要求逐行精读所有代码，但以下差异必须人工查看：

- 新增或修改公共接口、公共字段和静态状态；
- 新增具体职业、UI、场景、网络或全局管理器依赖；
- 对象创建、销毁、事件订阅和注销；
- 场景、预制体、`.meta`、GUID、Animator 和 Project Settings；
- 伤害、冷却、资源扣除、交互占用和网络权威；
- 新包、新程序集和目录迁移；
- 工单之外的文件变化。

看不懂的核心差异应先要求解释和补测试，不得直接合并。

### 3.4 进行 Unity 实际验收

用户最终判断：

- 编译和测试是否通过；
- 预制体与场景是否缺少引用；
- 操作和动画是否符合预期；
- 战争迷雾、导航和交互是否在真实场景中工作；
- 是否出现原来没有的问题；
- 是否达到本工单的完成定义。

### 3.5 保留视觉与手感工作

关卡构图、地标可读性、镜头、操作手感、动画衔接、特效可读性和 Boss 节奏仍由用户主导。这些不是低效杂务，而是游戏开发的核心创作工作。

### 3.6 确认项目记忆

每轮结束后确认事实基线、交接、任务状态和提交记录是否一致。聊天记录只作讨论材料，不能替代仓库事实。

## 4. 标准开发循环

```text
用户确定一个结果
  ↓
K3.1 Pro 核对事实、收敛方案、生成 S/M 级工单
  ↓
用户确认目标、非目标、文件边界、编辑器影响和验收
  ↓
OpenCode＋DeepSeek 在本地任务分支实施
  ↓
DeepSeek 提交 diff、真实测试和未验证项
  ↓
K3.1 Pro 独立会话审查工单、契约和 diff
  ↓
用户检查高风险差异
  ↓
Unity 编译、自动测试、PlayMode 与视觉验收
  ↓
通过：更新文档、成本记录和本地提交
失败：结构化反馈，最多一轮修复；第二轮失败停止
```

### 4.1 开工前六问

任何一项无法回答，就先不启动编码：

1. 本轮唯一主要结果是什么？
2. 明确不做什么？
3. 最多允许修改哪些文件？
4. 必须保持哪些现有行为？
5. 如何证明完成？
6. 失败后在哪里停止？

### 4.2 结构化问题反馈

```text
场景与对象：
前置状态：
复现步骤：
预期结果：
实际结果：
Console 完整错误：
截图或录像：
最近一次相关修改：
本轮要求：先定位并做最小修复，不重写整个系统。
```

### 4.3 每轮成本记录

记录任务 ID、执行模型、实现轮次、修改文件数、测试状态、人工修复时间、审查问题和最终验收状态。评价工具的依据是**验收通过成本**，不是代码生成速度。

## 5. 本阶段“毕设基石”的定义

本阶段完成不等于整个游戏完成，而是形成一个可以从这里稳定展开毕业设计的工程底座。

### 5.1 必须达到

1. **稳定基线**：明确 Unity 与包版本、启动场景、操作方式和可回退提交。
2. **行为基线**：现有编队、移动、攻击、救援、迷雾、宝箱和场景切换的实际状态被记录，不混淆“代码存在”和“验收完成”。
3. **边界明确**：Core、Content、Gameplay、App、UI、Net、Editor、Tests 的职责和依赖方向可说明。
4. **生命周期明确**：应用、局内、楼层和单位状态的创建与清理责任明确。
5. **单位查询统一**：新代码不再通过逐帧全场扫描寻找单位；注册、注销和楼层隔离有测试。
6. **交互可扩展**：至少一种现有交互通过统一契约运行，具体目标不直接读取输入、选择器和 UI。
7. **技能解耦起步**：至少一个现有技能通过新上下文运行，效果不直接依赖具体武器、怪物和 `GameData`。
8. **池化有归还契约**：至少一类高频生成物通过连续借还测试，无状态残留。
9. **编辑器校验可用**：至少能自动检查关键空引用、数据 ID、单位预制体或 Animator 中的真实问题。
10. **测试入口存在**：有最小 EditMode／PlayMode 测试或独立测试场景，失败能定位。
11. **资产安全**：目录和数据迁移保留 `.meta`/GUID，不用文本替换猜改资产引用。
12. **文档同步**：已实现、重构中、待验证和暂缓项分开记录。

### 5.2 明确不属于本阶段

- 新增大量职业和完整技能组；
- 制作三层正式美术地图；
- 完成两个多阶段 Boss 的全部内容；
- 完整 2～4 人联机；
- 开发程序生成地牢、自研行为树编辑器或通用可视化脚本框架；
- 为“架构漂亮”一次性拆出大量程序集；
- 同时更换渲染管线、网络框架和动画方案。

### 5.3 扩展性最终验收

至少完成以下三个小实验：

1. **第四职业实验**：复用现有输入、选择、伤害、HUD 和动画公共拓扑，只增加必要数据、模型和效果；记录实际需要修改的文件。
2. **新交互实验**：增加一个简单交互目标，不修改选择器和输入核心。
3. **新测试场景实验**：通过模板建立场景，不复制整套应用管理器，并通过场景校验。

如果新增内容仍需要修改大量无关核心类，就不能宣称扩展性达标。

## 6. 基石重构推荐顺序

以下任务都必须进一步拆成 S/M 级工单，不允许整行一次性交给 Agent。

### FND-00：冻结事实与可回退基线

- 记录当前提交、Unity、包、场景和已有能力；
- 备份并验证工程能启动；
- 建立当前行为清单和已知问题；
- 建立 `Docs/Tasks`、`Docs/QA`、`Docs/Decisions` 和交接快照；
- 本任务不重构代码。

**退出条件**：干净副本能按说明启动；用户知道当前哪些功能确实可运行。

### FND-01：Unity 6.3 独立迁移

- 只在独立副本或迁移分支处理；
- 先核对包兼容，再处理编译、渲染、Cinemachine 和资产引用；
- 不同时重构玩法；
- 保存迁移前后截图、日志和 PlayMode 结果。

**退出条件**：同一行为基线在目标版本复验；若迁移阻塞，保留旧基线，不在迁移分支继续堆功能。

### FND-02：只读工程体检与最小测试入口

优先实现只读工具，不先做自动修复：

1. Project Doctor 的最小版本；
2. Content Validator 的稳定 ID 和必填引用检查；
3. Unit Prefab Validator 的关键组件检查；
4. Animator Audit 的状态、参数和 Override 检查；
5. 一个最小测试场景或测试运行入口。

**退出条件**：故意制造一个错误时工具能定位；修复后对应报告消失；不误报白名单。

### FND-03：单位注册与生命周期

拆分顺序：

1. 定义单位身份、注册和注销；
2. 只接入一个单位类型并测试；
3. 替换一个查询消费者；
4. 逐个替换 AI、迷雾、团灭和救援等查询；
5. 验证销毁、回收、倒地、跨层和重复注册。

**禁止**：一张工单同时替换所有系统并重写空间索引。先用简单正确实现，确有性能证据再优化。

### FND-04：统一交互的最小垂直切片

- 先冻结条件、开始、完成、取消、占用和打断契约；
- 选择宝箱或救援中的一个作为首个适配器；
- 保持现有 RTS 操作方式；
- 第二种交互用于证明复用；
- UI 只订阅状态，不由目标直接打开具体面板。

**退出条件**：完成、取消、距离不足、目标失效、重复交互和死亡打断有结果记录。

### FND-05：池化生命周期

- 明确 `OnRent`／`OnReturn` 或等价重置契约；
- 先处理一种飘字或特效；
- 检查目标、计时器、Trail、材质、事件订阅和楼层状态；
- 连续借还测试后再扩展到投射物。

### FND-06：技能上下文与一个技能迁移

- 先列出现有公共入口、调用方和必须保持的行为；
- 建立最小 `AbilityContext` 与能力接口；
- 只迁移一个现有技能；
- 保持消耗、冷却、动作和命中表现；
- 第二个技能用于发现契约遗漏，不立即重写全部技能。

**退出条件**：效果不再直调具体武器、怪物和全局消息；取消、死亡和重复施法规则有记录。

### FND-07：场景、数据和预制体生产基础

- 建立测试场景模板和必要场景校验；
- 需要迁移 `Date → Data` 时先干运行并保留 GUID；
- 建立基础单位预制体规范，不批量重建所有资产；
- 最后再按真实依赖增加少量程序集。

### FND-08：基石验收与冻结

- 执行第四职业、新交互、新测试场景三个扩展实验；
- 汇总测试、截图、工具报告和已知债务；
- 冻结公共契约和防回退规则；
- 形成“毕设内容开发从这里开始”的稳定提交。

## 7. 编辑器工具的人工协作规则

### 7.1 工具优先级

遵循：**只读检查 → 报告与定位 → 干运行 → 可撤销写入 → 批量生成。**

不要首先开发“一键重建整个项目”。本阶段优先：

1. 工程与引用检查；
2. 数据、预制体和 Animator 校验；
3. 测试场景模板；
4. 重复预制体结构的确定性创建；
5. 测试与报告入口。

### 7.2 工具任务必须具备

- 明确输入、输出和作用范围；
- 涉及写资产时提供干运行、备份或撤销策略；
- 错误能定位到具体资产或对象；
- 至少一个故意制造错误的测试；
- 不修改非目标资产的证明；
- 简短使用说明和验收截图。

### 7.3 人工编辑器步骤的工单规则

如果任务需要 Unity 操作，K3.1 Pro 必须在工单中列出“编辑器影响”。OpenCode 应优先使用现有工具；无法自动化时，必须给出完整对象路径、组件、字段、值和预期结果。

重复出现或步骤较多的机械操作，应另立工具任务，不在每个功能工单里重新手工执行。

### 7.4 场景与预制体安全

- 不让 Agent 凭空生成大段场景或 Controller YAML；
- 优先通过可复查编辑器脚本修改；
- 场景、预制体和 Animator 指定唯一修改者；
- 保留 `.meta`、GUID 和需要兼容的公共字段；
- 大规模场景调整与代码重构分开提交；
- 实际层级与工单不一致时停止，不复制对象“补齐”。

## 11. 完成定义与停止条件

### 11.1 完成定义

只有同时满足以下条件，任务才能标为完成：

1. 目标完成且未越界；
2. 指定测试真实通过；
3. Unity 手动验收有操作与结果；
4. 无新增关键空引用、重复订阅和池化残留；
5. GUID、公共字段、内容 ID 和动画状态符合要求；
6. 审查中的阻断和高优先级问题已关闭；
7. 文档与交接已同步；
8. 用户确认本地提交和下一任务。

### 11.2 立即停止的情况

- Agent 开始无边界全仓阅读；
- 修改文件超过工单；
- 为一个小修复引入新包或新系统；
- 同一测试两轮失败且没有新证据；
- 需要修改公共契约但工单未允许；
- 实际项目与基线不符；
- 编辑器步骤不断增加且无法确认对象状态；
- 消耗明显高于同类任务；
- 用户已经无法解释本轮差异。

停止后保留差异和日志，由 K3.1 Pro 判断“缩小任务、补充基线、改走工具任务或人工定位”，不要在原会话反复发送“继续修好”。

## 12. 每周节奏与防拖延规则

1. 每周只设一个可演示的工程结果，不设“完成架构重构”这种模糊目标。
2. 每周保留一个已验收稳定构建，不让主分支长期处于不可运行状态。
3. 规划、编码、审查和验收分开进行，避免在同一聊天中无限改方案。
4. 编辑器机械操作集中批处理，并记录哪些步骤应沉淀为工具。
5. 一次只让一个 Agent 修改一个任务，避免并行污染场景和预制体。
6. 出现新视频、新商业游戏方案或新模型时，先进入“待评估”，不立即插入当前工单。
7. 基石验收后冻结核心契约，再开始内容扩张；不要永远停留在重构阶段。

## 13. 现在就可以开始的第一轮

### 第一步：用户

- 确认当前可运行提交并保留备份；
- 记录现有能运行与不能运行的功能；
- 不新增职业、地图、Boss 或联机内容。

### 第二步：K3.1 Pro

只生成 `FND-00` 基线任务和 `FND-02` 的一个只读校验工具工单。若 Unity 6.3 迁移尚未完成，迁移仍独立进行，不与工具开发混合。

### 第三步：OpenCode＋DeepSeek

优先完成一个**只读、能发现真实问题、不会写资产**的最小校验器，例如单位预制体关键组件检查。它比全项目自动重构更适合作为 Agent 新流程的第一个任务。

### 第四步：独立审查与用户验收

- 故意给一个测试预制体移除必要组件；
- 工具应定位到该预制体和缺失项；
- 恢复组件后报告应消失；
- 检查工具没有修改任何资产；
- 保存报告、diff、测试结果和人工耗时。

### 第五步：沉淀流程

如果第一轮仍出现全仓扫描、越界修改或大量人工步骤，先修工单和工具边界，不急着进入技能系统重构。

## 14. 最终自我检查

开始每个任务前，用户只需问自己：

> 我是在推动一个可验收结果，还是又在让 AI 生成一批我可能无法维护的代码？

任务结束前再问：

> 我是否知道它改了什么、为什么这样改、如何回退，以及下一步新增内容是否真的更容易？

如果这两个问题都能明确回答，Agent 工作流才真正成为了开发能力，而不只是代码生成速度。
