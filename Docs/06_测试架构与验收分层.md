# 06 测试架构与验收分层

> 本文描述 `Assets/_Project/Tests/` 的**现状架构**与**约束**，不是路线图。凡是“现在还没做到”的，文中都会明确写出。
> 相关入口：规则书 `AGENTS.md` §3/§4；任务模板与 AC 表 `Docs/Handoff/TASK_*.md`；新手模板 `Assets/_Project/Tests/QaTestTemplate.md`。

## 1. 分层：L0 冒烟 / L1 回归 / L2 故障注入 / 功能套件

四层是**验收成本**分层，不是代码分层：同一套 Qa 公共层（`Tests/QA/`）与同一套证据格式被四层共用。

| 层 | 目的 | 当前入口 | 通过判据 | 典型耗时 |
|---|---|---|---|---|
| **L0 冒烟** | 证明“夹具 → 断言 → 证据 → 收尾”链路本身是通的，与产品行为无关 | `Tools/QA/In-Editor/<任一守卫>` 一次运行 | 该次 `InEditorResult.txt` 有 `code` 与 `evidenceSubdir`；`*_Assertions.jsonl` 行数 > 0 且与 Summary 的 `pass+fail+blocked+infraFail+observed` 一致 | 秒级~1 分钟 |
| **L1 回归** | 证明产品行为没被改坏（四套守卫全量断言） | `Tools/QA/In-Editor/{SPEC01 (green), REFACTOR, FND00B06, DIAG}` | SPEC01 `12/0`、REFACTOR `16/0`、FND00B06 `12/0 + observed 2`、DIAG `6/1`（唯一红 `Diag.Input.FirstExit`，`status=product_fail`，已知产品缺陷）；同一入口连续 ≥2 次结果一致 | 每次 1–5 分钟 |
| **L2 故障注入** | 证明“测试基础设施自己不骗人”：域重载、runner 丢失、preflight 超时等异常路径有确定收场 | 见下方三条注入法 | 收场留痕可查：`InEditorResult.txt` 的 `code` + `reason`（`runner-lost-domain-reload` / `preflight-timeout`），编辑器不被误杀；批次模式下进程退出码 = 写入值 | 分钟级 |
| **功能套件** | 单个 feature 的窄口径守卫，条数少、意图单一 | 历史：`FND00B04_*`、`FND00B05_*`、`FND02A_*`；新 feature 按本文 §4 新增 | 该 feature 的 TASK §3 AC 表逐条成立 | 秒级 |

**L2 的三条注入法（现状可复现）**

1. **域重载**：`Tools/QA/In-Editor/DIAG` 进入 Play 后，对任一测试脚本做“加一行注释 → 保存 → 等域重载 → 删回该行 → 保存”的**净零改动**，观察收场。
   预期分支：脚本重载使 Unity 退出 Play → `EnteredEditMode` 分支收场；若 runner 在重载中丢失，看门狗落 `code=3 + reason=runner-lost-domain-reload`。**净零改动**必须用 `git diff` 自证。
2. **runner 丢失**：Play 中手动删除 `<Suite>_Runner` GameObject，3s 宽限后看门狗必须落 `code=3 + reason=runner-lost-domain-reload` 并退出 Play（编辑器内不退出编辑器）。
3. **preflight 超时**：菜单触发后让编辑器持续编译/资产刷新超过 120s，必须落 `InEditorResult.txt` 的 `reason=preflight-timeout`，不进入 Play。

> L2 不算产品断言，不写进套件的 `*_Assertions.jsonl`；它的证据是 `InEditorResult.txt` + Console 摘录。

## 2. 套件契约：夹具 + 断言 + 证据 + 注册式边界

一个守卫套件由**五件**组成，缺一件就不算套件：

| # | 组成 | 位置 | 硬约束 |
|---|---|---|---|
| 1 | 证据适配器 `<Suite>_Evidence : QaEvidence` | `Tests/<Suite>/Runtime/<Suite>_Evidence.cs` | ≤40 行，只组装 `QaEvidenceSpec`；不含 `File.`/`Directory.`/JSON 拼装/计分 |
| 2 | 断言 `Assert<Domain><Behavior>(IQaSink sink, …)` | `<Suite>_ProbeRunner.cs` | 证据只经 `IQaSink`；夹具显式入参；体内零 `File.`/`Directory.`/`SessionState`/`EditorApplication`/`QaLauncher`/`*_Boot` |
| 3 | 编排（`Start` / `Finish` / 看门狗） | `<Suite>_ProbeRunner.cs` | 允许用 `SessionState` 写 `Finished`/`ExitCode`；不允许把引导逻辑塞进断言 |
| 4 | 注册表 `QaLaunchSpec` | `Tests/QA/Editor/QaLauncher.cs` | `SuiteId`/`KeyPrefix`/`RunnerName`/`RunnerType`/证据目录/环境变量/`Launch` 一次声明，禁止在别处再硬编码同一套件 |
| 5 | 菜单转发 `[MenuItem]` | `Tests/QA/Editor/QA_InEditorMenu.cs` | 一个套件一个转发方法，只调 `Run("<SuiteId>")` |

**注册式边界（必须照此理解，不要写成“完全无需改代码”）**

Unity 的 `[MenuItem]` 是编译期特性，**不能在运行时动态注册**。因此“注册式”的实际含义是：

- 新增套件 = ①注册表加一条 `QaLaunchSpec` ②加一个 `[MenuItem]` 转发方法；
- **不需要改**：preflight 等待（编译/资产刷新/域重载三重判据）、证据子目录递增（`editor_runN`）、`TryFinish` 收尾、`runInBackground` 记录/还原、看门狗与退出分叉。
- 换句话说，**驱动逻辑是唯一实现**，套件只是数据 + 入口；新增套件的 diff 必须落在这两处之内。

**证据契约（现状，逐字符固定）**

| 套件 | 证据目录 | 断言文件 | Summary | ExitCode | Runs 索引 |
|---|---|---|---|---|---|
| SPEC01 | `Docs/QA/Evidence/SPEC-01/` | `SPEC01_Assertions.jsonl` | `SPEC01_Summary_run<N>.json` | `SPEC01_ExitCode_run<N>.txt` | `SPEC01_Runs.jsonl` |
| REFACTOR | `Docs/QA/Evidence/REFACTOR-M<里程碑>/` | `REFACTOR_Assertions.jsonl` | `REFACTOR_Summary_run<N>.json` | `REFACTOR_ExitCode_run<N>.txt` | `REFACTOR_Runs.jsonl` |
| FND00B06 | `Docs/QA/Evidence/FND-00B-06/` | `06_Assertions.jsonl` | `06_Summary_run<N>.json` | `06_ExitCode_run<N>.txt` | 不生成 |
| DIAG | `Docs/QA/Evidence/DIAG-SKILL/` | `DIAG_Assertions.jsonl` | `DIAG_Summary.json` | `DIAG_ExitCode.txt` | 不生成 |

- 编辑器内运行时，`QA_InEditorMenu` 注入 `QA_EVIDENCE_SUBDIR=editor_runN`（扫描既有目录递增，**不覆盖历史证据**）。
- 断言行字段顺序：`run, [前置字段…], qaItem, assertion, expected, actual, pass, status, kind, timestamp, data`；前置字段只有声明了才出现（REFACTOR 的 `milestone`）。
- 计分口径：`infra_fail→Infra`、`blocked→Blocked`、`observed→Observed`，其余按 `pass` 真值分 `Pass`/`Fail`。

## 3. 断言 ID 规范：`<Domain>.<Behavior>`

- `Domain` = 被测面向（`Skill` / `Clock` / `Animation` / `UI` / `Locomotion` / `Attack` / `Party` / `Combat` / `Diag` / `Regression`），按“行为领域”分，不按文件、不按人分。
- `Behavior` = 被观察的行为名，不写期望结果（禁止 `ShouldPass` / `Fix` / `OK`）。
- 同一 ID 在 `Record(qaItem, assertion, …)` 的 `qaItem` 与 `assertion` 上通常同值；分档套件（FND00B06 的 `4` / `6`）把档位写进 `qaItem`。
- **ID 与 TASK §3 AC 表一一对应**：AC 表里写的断言 ID 就是 `Record` 的第一个参数，不允许只在代码里另起名字。

真实例子与归属：

| 断言 ID | 所在套件 | 对应 AC / 口径 |
|---|---|---|
| `Skill.CastSmoke` | SPEC01 | SPEC-01 技能施放冒烟（失败施放不扣蓝、Q/W 效果链、E/R 空槽静默） |
| `Diag.Input.FirstExit` | DIAG | DIAG 输入链首个失效节点（当前唯一红，`status=product_fail`，属产品缺陷不属测试缺陷） |
| `Party.PresentAndMove` | REFACTOR | 队伍三人在场并可被生产移动命令驱动 |
| `Locomotion.AllPlayersMoveParam` | SPEC01 | Locomotion 混合树 1D / `SpeedZ` / 阈值 0,4 |
| `Clock.MeleeNormalizedWindow` | SPEC01 | 近战命中由 `AttackMelee` 归一化窗口驱动 |
| `UI.SpawnAnchor` | SPEC01 | 伤害飘字挂载锚点 |

命名的实际约束（来自本单“断言零变化”要求）：**ID、`expected` 字面量、阈值、通过条件一旦进过 `Docs/QA/Evidence/**` 就不再改**。

## 4. 扩展规则

1. **新功能 = 新套件**：新 feature 不复用别人的断言 ID，也不往既有套件里塞“顺便测一下”。套件命名 `<FND 编号>_ProbeRunner` / `Test*` 沿用现状，证据目录新建 `Docs/QA/Evidence/<任务号>/`。
2. **行为变更必须留痕**：
   - 旧断言**不得静默修改**（改 `expected`、改阈值、放宽判定、把红改绿）；
   - 只能两条路：**新增**断言表达新口径，或**显式改口径**——在 TASK/REPORT 里写清旧口径、新口径、为什么改，并在证据目录留改前/改后两轮 JSONL；
   - 口径变更后必须重跑同入口 ≥2 次，结果一致才算成立（时序类）。
3. **断言只经 `IQaSink`**：新增断言不得直接写盘、不得读 `SessionState`、不得依赖 `QaLauncher`/`*_Boot`，否则 M7 拆程序集时无法搬走。
4. **去重纪律**：合并重复实现前必须能证明逐分支等价（参数、默认值、边界都要一致）；不能等价就留在原套件，并在 REPORT 记“未合并及原因”。
5. **不改驱动**：preflight、子目录递增、`TryFinish`、看门狗、`runInBackground` 五处属于驱动逻辑，新增套件不许动它们。

## 5. 证据 schema 版本化

**现状（必须如实记录）**：断言行与 Summary **还没有显式 `schemaVersion` 字段**。当前兼容性靠“逐字符保留既有字段名/键序/文件名”保证——这是 `QA-REFACTOR-01` 的 AC-3 判据，也是 canonical 证据能跨轮比对的前提。

当前 schema（视为 **v1**，隐式）：

| 部件 | v1 定义 |
|---|---|
| 断言行 | `run, [前置字段…], qaItem, assertion, expected, actual, pass, status, kind, timestamp, data`；UTF-8 无 BOM、行尾 `\n` |
| Summary | 每套件固定键序（见 `QaEvidenceSpec.SummaryFields`），SPEC01 保留重复的 `mode` 键（现状，禁止“顺手修”） |
| 文件名 | 见 §2 表；文件名本身是 schema 的一部分（外部脚本按名字取文件） |
| Runs 索引 | 可选，字段 `[前置字段…], mode, run, pass, fail, blocked, infraFail, observed, summary, exitReason, finishedAt` |

**版本化策略（引入 `schemaVersion` 时必须遵守）**：

1. **只追加、不改序**：新字段只能追加在 `data` 内或断言行末尾；既有键名、键序、文件名不改。读方必须**忽略未知字段**，不得因多一个字段报错。
2. **缺省即 v1**：没有 `schemaVersion` 的历史文件按 `1` 解释；新增字段后老证据仍然可读。
3. **破坏性变更 = 换文件名/换目录**：一旦需要改字段语义或键序，不原地改，改为新文件名（或新 tag/新 `editor_runN` 子目录）并保留旧文件。
4. **canonical 只追加**：`Docs/QA/Evidence/**` 既有文件不删、不改、不覆盖；重跑一律写新子目录/新 run 号，比对用复制出来的快照。
5. **schema 变更要留痕**：写进当轮 TASK/REPORT，并在证据目录留“旧格式样本 + 新格式样本”。

## 6. 构建隔离（M7 目标态与现状）

**现状**

- `Assets/` 下**没有任何 `.asmdef`**：产品代码在预定义程序集 `Assembly-CSharp`，编辑器工具在 `Assembly-CSharp-Editor`。
- `Tests/**` 同样没有 asmdef，所以：`Tests/*/Runtime/` 的代码随 `Assembly-CSharp` 编译（构建时会一起进包），`Tests/*/Editor/` 与 `Tests/QA/Editor/`（`QaLauncher`、`QA_InEditorMenu`）随 `Assembly-CSharp-Editor`，只在编辑器编译。
- 因此现在**不能**把 `Tests/` 单独拆成 asmdef：Unity 的 asmdef 程序集**不能引用预定义程序集** `Assembly-CSharp`；产品代码没有自己的 asmdef，测试 asmdef 就找不到 `UnitHealth`/`CharacterBrain` 这些类型，必然编译红。

**M7 目标态**

1. 产品代码先拆 asmdef（至少 `Core` / `Units` / `Combat` / `Skills` / `UI` 这类边界），`Assembly-CSharp` 不再承载业务代码。
2. `Tests/` 建立 `tests asmdef`（`Tests/QA` 公共层与四个守卫分属 runtime/editor 两个 asmdef），`references` 指向产品 asmdef。
3. 用 `UNITY_INCLUDE_TESTS` 约束测试程序集的**构建包含**：编辑器与 `-runTests`/batchmode 下编译，正式 player 构建不包含测试代码。
4. 断言已经按 `IQaSink` 出证据、不依赖引导（`AGENTS.md` §3.2.1、`QA-REFACTOR-01` AC-10），因此 M7 后可以把断言直接包成 `[UnityTest]`；**这一步现在不做**，本文件只登记边界与前置条件。

**短期保障（在 asmdef 落地前）**

- 编辑器专属逻辑一律放 `Editor/` 目录（编译期隔离）；
- 需要在 player 里不生效的运行期钩子用 `#if UNITY_EDITOR` 包住（例如 `SPEC01_BootHook`）；
- 断言禁止直接写盘/读引导状态，保证“搬程序集”是纯机械操作。
