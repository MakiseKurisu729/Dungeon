# 工作流细则

> 由 `AGENTS.md` 索引。本文件承载**模板与格式**（TASK 三节 / REPORT / 证据 / 提交分支 / 前置清单 / 风险 / 讲稿 / Replan / Done）；硬约束以 `AGENTS.md` 为准，冲突时 AGENTS 胜。
> 最后更新：2026-11-05（WF-05 MCP 常开编辑器规则）

## 1. TASK 模板要求

模板：`Docs/Handoff/TASK_TEMPLATE.md`（复制后填写）。`Docs/Handoff/TASK_<ID>.md` 必须**自包含**（执行者只读这一份即可干活）。

结构固定为**三节 + 执行信息 + 学习产出**，与课程 `specs/<feature>/{requirements, plan, validation}.md` 一一对应：

| 本模板节 | 对应课程文件 | 内容 |
|---|---|---|
| §0 元信息 | — | ID、风险（常规/高风险）、授权、基线提交、回滚锚、分支、状态 |
| §1 需求 | `specs/<feature>/requirements.md` | 一句话目标、用户故事、`R-1..n`、不在范围、约束 |
| §2 方案 | `specs/<feature>/plan.md` | 至少 A/B 两案 + 取舍、数据流、影响面清单、实施顺序、风险与回滚 |
| §3 验证 | `specs/<feature>/validation.md` | AC 表 + 运行次数 + 必须保存的证据 |
| §4 执行 | — | 前置、允许改动/读取、绝不触碰、证据目录、熔断、预算 |
| §5 学习产出 | — | 讲稿要求 / 不适用理由、三句话版本 |

旧的“风险等级 / 目标 / 允许改动 / 验收 / 回滚锚”等要素**仍在**，只是归入上述节次，不再单列。

保留要素：

| 节 | 内容 |
|---|---|
| 风险等级 | `常规` / `高风险`（见 §6） |
| 授权与前置 | 所有者批准日期、前置提交、工作区假设 |
| 允许改动的文件 | 表格：文件 + 动作（新增/修改/移动/归档） |
| 允许读取 | 本单特批可读的文档清单（默认只读工单） |
| 硬边界 | 绝不触碰：`Assets/**`、`ProjectSettings/**`、`Packages/**`、`CURRENT.md`、其他 `TASK_*`/`REPORT_*`/证据 |
| 回滚锚 | 回滚到哪个提交 / 如何撤销 |
| 影响面清单 | 新文件 / 符号 / 字符串引用 / 场景引用 / `.meta` |
| 熔断 | 本单特有的停止条件 |
| 建议提交（预览） | 标题 + 正文一行“为什么” |

质量规则：

- “优化架构”“完善战斗”“做好 Boss”不是可执行目标。
- 验收不能只写“无报错”，必须列操作、预期、边界条件。
- 重构必须列出不允许变化的现有行为。
- Unity 资产任务必须保护 GUID、公共字段、场景引用、动画状态名。
- 基线与工单不符时先停止并报告，不按旧聊天继续。
- 数量与风险：单张工单默认 ≤3 个文件；L 级任务必须先拆成 S/M；文件数量与风险分开判断（见 AGENTS §5）。
- **方案节至少两个备选**：只有一个可行时也要写“为什么另一个不可行”，不省对比。
- **AC 表先定**：需求无法写成 AC 时，先回去把需求写清楚，不带着模糊验收开工。

### 1.1 执行预算与开工前六问

1. 计划不超过 8 行，先确认最小修改路径。
2. 一轮实现 + 工单指定的最小测试 + **最多一轮修复**；第二轮仍失败即停，保留差异并报告。
3. 不反复运行完整 Unity 测试/构建；不为“顺便优化”扩大文件范围。
4. 达到用户设定的额度、时间或文件数上限立即停止。
5. 开工前必须能回答：唯一主要结果 / 明确不做什么 / 允许改哪些文件 / 必须保持哪些旧行为 / 如何证明完成 / 失败后在哪里停。任一项答不出就先不开工。

### 1.2 问题反馈模板（用户 → 大脑）

```text
场景与对象：
前置状态：
复现步骤：
预期结果：
实际结果：
Console 完整错误：
截图或录像：
最近一次相关修改：
本轮要求：先定位并做最小修复，不重写整个系统。
```


### 1.3 AC 表规范（验证节）

每条验收写成一行，四列缺一不可：

| AC | Given / When / Then | 断言 ID | 证据 |
|---|---|---|---|
| AC-1 | 给定…，当…，则… | `Skill.CastSmoke` | `Docs/QA/Evidence/<ID>/run1/…` |

1. **Given/When/Then**：前置状态、触发动作、可观察结果。结果必须是数据（次数、数值、状态位），不是“看起来正常”。
2. **断言 ID**：与测试方法或断言名称一致，便于 REPORT 回填与日志检索；没有自动化断言时写“目检-1”并说明原因。
3. **证据**：具体文件路径，不是目录名；时序类写清运行次数与 run 子目录。
4. 覆盖范围：至少 1 条主路径 + 1 条边界/失败路径；重构单另加“不允许变化的现有行为”条目。
5. AC 只增不减：执行中发现漏项，追加 AC-n 并在 REPORT 说明，不悄悄改旧条。

### 1.4 讲稿前置

TASK §5 必须表态：需要讲稿（feature / 高风险）或写“不适用 + 理由”。写“不适用”的，Done 时不再补。

## 2. REPORT 模板

路径：`Docs/Handoff/REPORT_<ID>.md`；模板：`Docs/Handoff/REPORT_TEMPLATE.md`。必含节：

1. **结果摘要** —— 完成 / 部分完成 / 失败 / 阻塞，一句话结论。
2. **AC 回填表** —— `AC | 结果 | 断言 ID | 关键数据 | 日志路径`，逐行对应 TASK §3；未运行写“未运行”+ 原因。
3. **实现原理（面向项目所有者）** —— 按下述清单作答，不设字数上限，讲清即止。
4. **受影响模块导航** —— 模块职责、入口（类/方法/场景对象）、数据流（输入 → 处理 → 输出），≤200 字；附改动文件清单，与 TASK §4 逐项比对。
5. **证据清单** —— 逐个文件列路径与内容；运行次数。
6. **学习讲稿** —— 链接 `Docs/Learning/<ID>_讲稿.md`；不适用须写明理由。
7. **未决项** —— 遗留问题、缺项、待目检项（≤3）。
8. **建议提交** —— 见 §3。
9. **消耗记录** —— 钱包（Go 订阅 / Zen 按量）+ 模型完整 ID。

实现原理必答清单（第 3 节）：

| # | 必须回答 |
|---|---|
| 1 | 根因 / 目标：改之前是什么问题，或这次建立什么能力 |
| 2 | 备选方案与为什么没选（A 为什么不行、B 为什么选） |
| 3 | 实际数据流：输入 → 处理 → 输出 |
| 4 | **3–5 个关键代码位置（`文件:行`）**，每处一句话说明在干嘛 |
| 5 | 边界 / 失败模式：什么情况会坏，现在怎么挡住 |
| 6 | 与 TASK §2 计划的差异及原因 |
| 7 | **三句话版本**：答辩时先讲这三句 |

纯验收 / 纯文档单：第 3、4 节可写“不适用”，第 6 节写“不适用 + 理由”。

### 2.1 学习讲稿

模板：`Docs/Learning/TEMPLATE_讲稿.md`；命名 `Docs/Learning/<ID>_讲稿.md`；篇幅 1–2 页。

1. **分工**：AI 出初稿（结构 + 关键代码定位），所有者**用自己的话改写**。改不动的地方就是没懂，让 AI 再讲一遍。
2. **必含**：一句话、原来的问题、方案对比、数据流、关键代码 3–5 处（`文件:行`）、设计取舍、边界/失败模式、答辩 Q&A 5 条；名词表可选。
3. **触发**：feature / 高风险任务必须有；纯文档 / 纯巡检小修在 TASK §5 与 REPORT 第 6 节写“不适用”。
4. **位置纪律**：讲稿是 `Docs/Learning/` 的独立文件，不塞进 REPORT 正文；REPORT 只放链接。
5. **真实性**：讲稿里的代码位置与数据必须与交付代码一致；代码后续变了要同步更新讲稿。

## 3. 提交规范

1. 标题用**中文类型前缀**：`功能 / 修复 / 测试 / 文档 / 重构：一句话中文摘要`。不再使用英文 `type(scope)`（所有者 2026-11-05 明确要求“英文看不懂”）。
2. 正文：**一行“为什么”**（动机/根因），不写“做了什么”。
3. 默认**单提交**；用户用 GitHub Desktop 一键提交。不再要求分 hunk。
4. 混合改动（代码 + 测试 + 文档）仅在用户要求拆分时给分组清单：每组列 `git add` 文件与各自的提交信息。
5. 提交内容不得包含账号、密码、令牌、许可证文件或私人路径；`Library`/`Temp`/`Logs`/`obj` 等生成目录不入库。

```text
文档：收敛工作流规则到 AGENTS.md
为什么：流程规则散落在 8+ 个文件中且互相冲突，入口文件与当前状态不一致
```

拆分示例（仅在需要时使用）：

```text
组 1：
git add Assets/_Project/Scripts/Foo.cs Assets/_Project/Scripts/Foo.cs.meta
修复：修正普攻伤害重复结算
为什么：OnHit 在动画事件与协程中各调用一次，导致单次攻击结算两次。

组 2：
git add Docs/Handoff/REPORT_XXX.md Docs/QA/YYY.md
文档：登记 XXX 修复验收证据
为什么：修复结论需可追溯到断言与日志。
```

### 3.1 分支策略

1. **默认在当前分支工作**，不强制一 feature 一分支：Unity 场景 / 预制体合并成本高，短命分支只会制造合并冲突。
2. **例外**：纯代码重构（无场景/预制体/Animator/`.asset` 改动）可用短分支，产出后尽快合并并删除。
3. 资产改动一律由所有者在 Unity 中完成并提交，**不因资产另开分支**。
4. 分支名：`refactor/<scope>-<短描述>`；不使用个人前缀、不建长期并行分支。

## 4. 证据规范

1. 目录：`Docs/QA/Evidence/<TASK-ID>/`。
2. 每次运行产出：运行日志（`.log`）、机器可读结果（`.jsonl`）、`Summary.md`、`ExitCode.txt`。
3. **canonical 套件目录只追加不覆盖**：重跑写入带 tag 的子目录（如 `run2_green/`），禁止删除或覆盖既有证据。
4. 次数口径：常规验收同一入口连续 ≥2 次；间歇性/时序类 **N≥3**，且各次数据一致才算通过。
5. 证据必须能回答：跑了什么命令、期望什么、实际什么、原始输出在哪。
6. 验收类工单必须含固定节 **“自动化验收标准”**（可断言预期行为 + 实际数据 + 日志位置）与 **“人工目检清单”**（≤3 项，没有则写“无”）。

## 5. 前置清单

### 5.1 影响面闸门

动手编辑前输出：

| 项 | 内容 |
|---|---|
| 新增文件 | 路径 + 用途 |
| 修改符号 | 类 / 方法 / 字段 |
| 字符串引用 | Animator 参数名、`SendMessage`、`GameObject.Find`、事件名 |
| 场景/预制体引用 | 走 GUID 的对象与组件 |
| `.meta` | 是否随资产一起移动/重命名 |

用户确认后才编辑。纯 `Docs/` 单可由所有者在工单中预批。新增测试 `.cs` 引起的 `.csproj` 自动改动视为隐含延伸。

### 5.2 Unity 访问模式自证

与 `AGENTS.md` §3.2 / §3.2.1 同源，此处只写自证细则；冲突时 AGENTS 胜。模式二选一，由任务书声明，未声明按模式 A。

**模式 A｜batchmode（默认）**

- 编辑器打开着项目时**不得**做任何 Unity 操作。
- 自证：Unity 进程数 = 0，且 `Temp/UnityLockfile` 不存在。
- 长任务允许以自证替代人工确认；证据写进 REPORT。
- 需隔离副本时，操作前必须告知用户并说明代价；未告知不得动手。

**模式 B｜MCP 常开编辑器**

- 前置三条同时成立才可动手：① 任务书已声明模式 B 与授权范围；② 影响面清单已确认（§5.1）；③ 多实例时已 `set_active_instance` pin 到唯一实例。
- 只读白名单与写操作三件套以 `AGENTS.md` §3.2.1 为准；本条不重复列出，也不放宽。
- REPORT 必写 `editor_state` 记录：`instance_id`、`is_compiling`、`is_domain_reload_pending`、`play_mode`（取作业开始与结束两次）。
- 域重载未完成（`is_compiling` 仍为 true）时，不得继续任何写操作或验收判定。
- 模式 B 下，AI 可自行 `refresh_unity` / 聚焦唤醒编辑器，无需逐次询问；唤醒仅限让编辑器响应，不含任何资产改动。

### 5.3 资产改动清单格式

| 资产 | 路径 | 改动 | 风险 | 执行人 |
|---|---|---|---|---|
| 场景 / 预制体 / Animator / `.asset` | … | 字段 / 状态 / 引用 | GUID 或引用断裂 | 用户（AI 只出清单或编辑器工具） |

资产改动审批流程（所有者 2026-11-05 定）：

1. **出清单**：AI 按上表格式列出文件名、字段/组件、改动前后值、理由、回滚方式、影响面（是否动 GUID、是否影响场景引用）。
2. **大脑复核**：确认是否确有必要、是否可用代码替代、是否触碰架构不变量（触碰则先写 ADR）。
3. **所有者批准**：明确回复“批准”，或直接在子代理会话里批准。
4. **执行 + 读回**：批准后用 Unity 编辑器 / MCP 工具改，改完读回字段值并写进 REPORT；未批准的清单只能停留在提案状态。

补充：子代理在子会话里拿到的批准，必须在 REPORT 与回执中记录“谁批准 / 时间 / 内容”，大脑据此判断是否放行，不得只写“经批准”。

## 6. 风险两级与审查

| 等级 | 范围 | 审查 |
|---|---|---|
| 常规 | 脚本、测试、文档、孤立小改 | 大脑批末复审 |
| 高风险 | 场景、预制体、Animator、GUID、伤害管线、网络同步、`ProjectSettings` | 用户审阅；改架构不变量先写 ADR |

高风险追加审查清单：

- [ ] 伤害是否可能重复结算
- [ ] 消耗/冷却是否可能重复扣除或取消后错误返还
- [ ] 交互是否重复完成、占用不释放、目标死亡后继续
- [ ] 单位注销是否覆盖倒地、销毁、回收、跨层
- [ ] 场景/预制体是否出现 Missing Script / Missing Reference
- [ ] Animator 状态、参数、Override 是否仍一致
- [ ] 编辑器工具是否只修改声明的目标
- [ ] 是否保存了可回退提交

常规追加审查清单（代码/测试/文档）：

- [ ] 依赖方向正确，无具体职业/UI/场景/网络反向依赖
- [ ] 无新增静态全局状态、逐帧全场扫描
- [ ] 事件订阅与注销成对，对象池借还有重置
- [ ] 工单外无改动；测试真实运行，未运行的已写明
- [ ] 文档事实/历史/待验证分开；完成项有证据；旧方案未复活

## 7. 停止与熔断清单

与 `AGENTS.md` §6 同源，此处为可勾选版本：

- [ ] 单步重试 ≥3 次仍红
- [ ] 编译错误连续 ≥2 轮
- [ ] 计划外资产改动 / 装包 / 升引擎 / 目录迁移
- [ ] git 异常
- [ ] 配额撞限
- [ ] 模式 A 下 Unity 未关或状态不明
- [ ] 仓库与任务基线不符
- [ ] 同一命令重复 3 次无进展
- [ ] 修改文件数超过工单上限
- [ ] 需要改公共契约但工单未允许
- [ ] 模式 B 下调用了未授权写工具
- [ ] 域重载未完成继续操作（`isCompiling` 仍为 true）
- [ ] 同一 Unity 实例被两个会话同时驱动

停止后保留差异与日志，由大脑判断“缩小任务 / 补基线 / 转工具任务 / 人工定位”，不在原会话反复“继续修好”。

## 8. 工作流批次补充规则

### 8.1 文档命名与单一真相源

1. 文件名带职责前缀：`TASK_` / `REPORT_` / `QA_` / `EVIDENCE_`（`CURRENT.md`、编号设计文档 `00`～`05` 除外）。
2. 同一工件全仓唯一路径，禁止跨目录同名；任务包统一位于 `Docs/Handoff/TASK_*.md`（原 Docs/Tasks 已于 WF-01.1 并入并删除）。
3. 两文件内容冲突时，以“当前状态”文件 `Docs/Handoff/CURRENT.md` 为准。

### 8.2 TDD 前置

修复类与新功能工单执行顺序为“先写失败测试（red）→ 再实现到全绿”；测试资产沿用 `Assets/_Project/Tests/` 体系。

### 8.3 提案闸门

改动面较大的工单先生成提案（业务规则 + 未决问题清单），用户回复“批准”后才生成正式 TASK。

### 8.4 文档同步触发器

Unity/包/启动方式变化；公共类、字段、数据 ID、目录或程序集变化；新增/删除场景、预制体、Animator 状态或参数；项目范围或职业/楼层/首领规则变化；测试推翻旧假设；功能由“代码存在”变为“接线验收完成”；模型路由或套餐变化；冻结决策被 ADR 替换。

范围 / Mission / 技术栈发生变化 → 走 Replanning（§9），并同步 `Docs/Specs/constitution.md`。

## 9. Replanning（10 分钟清单）

每个 feature 标 `Done` 后做一次，防止路线图、constitution、规则与实际脱节。顺序固定：

| 分钟 | 动作 | 产物 |
|---|---|---|
| 0–2 | **路线图**：`Docs/02` 里程碑是否仍然成立？当前阶段 / 下一里程碑是谁 | 一句话结论；需要时改 `02` |
| 2–4 | **constitution**：Mission / Scope / Tech stack 是否还准确 | 需要时改 `Docs/Specs/constitution.md`（只此窗口改） |
| 4–6 | **规则与流程**：本轮是否出现规则没覆盖的情况？是否要加一条 | 改 `AGENTS.md` 或本文件；新不变量先写 ADR |
| 6–8 | **下个 feature**：给出一句话目标 + 是否在 Scope 内 + 风险等级 | 下一张 TASK 的输入 |
