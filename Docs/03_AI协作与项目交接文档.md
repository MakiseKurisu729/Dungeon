# 魔石地牢：AI 协作、成本控制与项目交接文档

> 文档版本：v2.0  
> 编制日期：2026-11-02  
> 适用范围：玩法讨论、架构设计、编码、Unity 接线、测试、审查、论文和跨会话交接  
> 基本原则：AI 负责提出建议和执行受控任务；用户负责需求决策、Unity 最终集成、测试验收、远端推送和费用决策。  
> 核心指标：不是“生成了多少代码”，而是**每个验收通过的任务消耗多少钱、多少额度、多少人工修复时间**。

## 1. 总体协作方案

采用“**低成本设计讨论＋统一架构与任务包＋一个主编码代理＋异构模型审查＋人工 Unity 验收**”。

```text
设计讨论 AI：发散玩法、寻找规则漏洞
        ↓
用户：决定做什么、不做什么
        ↓
架构 AI：收敛需求，生成小任务包、文件边界和验收标准
        ↓
主编码代理：在独立分支进行一轮实现和受控测试
        ↓
异构审查 AI：只审查任务包、代码差异和测试证据
        ↓
用户：Unity 编译、场景接线、运行验收
        ↓
架构 AI：更新事实基线、交接文档和下一任务
```

### 1.1 为什么不让一个模型包办

- 设计讨论需要发散和质疑，编码执行需要收敛和遵守约束，目标不同。
- 同一模型自己写、自己审，容易重复原有假设。
- 所有讨论都放进编码代理，会把本可用免费对话完成的工作消耗在昂贵额度里。
- 多模型协作必须通过文档和代码差异交接，不能依赖无限增长的聊天记录。

### 1.2 同时只保留一个主编码订阅

默认不同时订阅 Kimi Code、Codex、Claude Code、Cursor 等多个主执行工具。模型可以替换，**任务包、验收、分支和文档规范不随模型改变**。

## 2. 当前推荐分工

| 角色 | 当前推荐 | 主要任务 | 明确不做 |
|---|---|---|---|
| 玩法设计讨论 | DeepSeek 或其他低成本对话模型 | 职业、楼层、首领、撤离方案；找规则漏洞；提供多个选项 | 不直接决定需求；不凭记忆写 Unity 6.3 API |
| 架构与任务管理 | Kimi 长上下文对话 | 维护架构、事实基线、任务包、验收、研究材料和交接 | 不把规划写成已实现；不直接猜改场景 |
| 主编码候选 | Codex，先试用后决定 | 跨文件 C# 修改、行为保持型重构、自动测试、复杂 bug | 未验证成本前不直接购买长期订阅；不自由扩大任务 |
| 备用编码 | Kimi Code | XS/S 级小修改、明确单文件问题、已有额度下的简单任务 | 暂不做大型重构、三层地牢、完整职业/首领/联机任务 |
| 独立审查 | 与实现者不同家族的模型 | 审查差异、依赖、回归、测试证据；DeepSeek 可做低成本审查 | 不读完整仓库后重写架构；不沿用实现者结论 |
| 官方资料核查 | 具备检索能力的模型 | Unity、包迁移、API、许可证和文献核验 | 不用过时博客替代官方文档；不编造引用 |
| Unity 集成与验收 | 用户 | 导入、编译、接线、PlayMode、场景和动画验收 | 不把编辑器机械操作全部交给编码代理反复尝试 |

### 2.1 当前调整原因

已观察到 Kimi Code 在少量任务中消耗过快，单个任务可能触发滚动窗口限制。因此当前不再默认让它担任所有任务的主执行工具。滚动窗口、周限额和月度共享额度是不同限制，应以当前官方会员说明和账户页面为准。

### 2.2 角色不是永久品牌绑定

每 2～4 周或主套餐变化时，根据实际任务记录调整主工具。DeepSeek 也可以编码，Codex 也可以讨论方案，但为了避免成本和上下文混乱，同一任务仍只设一个主执行者。

## 3. 任务分级与路由

| 级别 | 任务范围 | 示例 | 推荐执行 |
|---|---|---|---|
| XS | 1 个明确位置，通常 1 个文件 | 改日志、修空引用、改一个小条件 | 现有低成本编码工具；通常无需二审 |
| S | 1～3 个文件，一个可观察行为 | 单技能解耦、替换一个扫描点、简单校验器 | 主编码候选或备用编码；按风险审查 |
| M | 约 3～6 个文件，涉及公共契约和测试 | `AbilityContext` 第一阶段、统一宝箱交互 | 主编码代理＋异构审查＋人工验收 |
| L | 超过 6 个文件、跨多个系统或资产 | 完整职业系统、三层地牢、完整联机 | 禁止一次交给编码代理，必须先拆成 S/M 任务 |

风险与文件数量分开判断：伤害结算、网络权威、GUID、场景和 Animator 即使只改一个文件，也按高风险处理。

## 4. 编码执行预算与停止规则

### 4.1 默认执行预算

每个编码任务必须带以下限制：

1. 计划不超过 8 行，先确认最小修改路径。
2. 只进行**一轮实现**。
3. 只运行任务指定的最小测试，不反复完整导入或构建 Unity 项目。
4. 测试失败后最多进行**一轮修复**。
5. 第二轮仍失败，停止并保留差异，报告错误、已尝试方案和下一步建议。
6. 不为“顺便优化”扩大文件范围，不更换架构继续尝试。
7. 达到用户预设额度、时间或修改文件上限时立即停止，不因“只差一点”继续消耗。

### 4.2 默认禁止事项

除非任务包明确允许，编码代理不得：

- 扫描整个仓库或反复读取无关文件；
- 读取 `Art`、StarterAssets、旧文档和生成目录来寻找一个小问题；
- 全量重写文件、批量格式化或修改无关代码；
- 安装新包、升级版本、替换框架；
- 同时做实现、无关重构、全面文档更新和多次提交；
- 反复运行完整 Unity 测试或构建；
- 修改非目标场景、预制体、Controller 和 Project Settings；
- 声称执行了实际上没有运行的测试。

### 4.3 异常消耗处理

出现以下任一情况立即停止：

- 代理开始第二轮以上大范围读文件；
- 修改文件数超过任务上限；
- 为修复一个小问题引入新系统或新包；
- 同一测试连续两轮失败且没有新信息；
- 实际行为与任务包基线不符；
- 消耗速度明显高于此前同类任务。

停止后由低成本对话模型分析日志和差异，再决定“缩小任务、换工具或人工处理”，不要在原会话里反复催促“继续修好”。

## 5. 成本控制策略

### 5.1 把昂贵额度只用于代码差异

玩法讨论、需求收敛、报错初步分析和文档整理优先在普通对话中完成。编码代理收到的应是短任务包和明确文件列表，不是几十轮聊天。

### 5.2 小上下文而不是全项目上下文

编码任务默认只提供：

- 根目录简短 `AGENTS.md`；
- 当前任务包；
- 直接相关代码和错误日志；
- 必须遵守的 1～2 个架构片段。

完整架构、任务书、旧 API 文档和研究资料由架构 AI 使用，不重复塞给编码代理。

### 5.3 订阅与 API 的使用边界

- 长时间、频繁编码优先使用当前已验证划算的一种订阅。
- API 适合短代码审查、测试用例生成、结构化分析和明确函数级任务。
- 不让按 token 计费的客户端无限制自主扫描全仓库。
- 价格、免费额度和模型能力会变化，不在项目文档中写死长期购买结论。

### 5.4 记录真实成本

每次编码任务保存：

| 字段 | 内容 |
|---|---|
| 任务 ID / 工具 / 日期 | 便于同类比较 |
| 起始与结束额度或费用 | 以账户显示为准 |
| 实际修改文件数 | 判断是否越界 |
| 自动测试结果 | 通过、失败、未运行 |
| 人工修复时间 | 包括 Unity 接线和清理 |
| 审查问题数 | 阻断/高/中/低 |
| 最终状态 | 验收、部分完成、失败、回退 |

**验收通过成本**应同时包含工具消耗和人工修复，不以生成速度代替质量。

## 6. 主编码工具对照测试

在决定长期订阅前，用独立分支让候选工具完成三个同类型、边界明确的任务：

1. 替换一个全场扫描为注册查询；
2. 将一个现有技能改为不直接依赖 `SwordSwing`；
3. 编写一个 Animator 或数据资产校验工具。

记录：

- 是否一次编译通过；
- 是否修改非目标文件；
- 是否保持现有行为；
- 测试是否真实运行；
- 人工修复处数和时间；
- 异构审查问题数；
- 实际额度或费用。

测试任务不得并行污染主分支。最终选择“完成合格任务成本最低”的工具，而不是只选生成最快或名气最大的工具。

## 7. 仓库内文档体系

```text
AGENTS.md                       当前硬约束、启动方式和防回退规则，保持简短
Docs/
  00_项目事实基线.md             当前版本、提交、真实能力、未验收项
  01_总体架构与内容生产规范.md
  02_迁移及实施计划.md
  03_AI协作与交接.md
  04_可复用资产与工具清单.md
  Decisions/                   ADR：重要且不易逆转的决策
  Tasks/                       任务包、执行预算和完成记录
  QA/                          回归矩阵、日志、截图、性能与联机结果
  Handoff/                     阶段性交接快照
  AI-Cost/                     工具消耗、对照测试和路由调整记录
```

### 7.1 三类信息必须分开

- **事实基线**：实际文件、版本、提交和已执行测试。
- **历史决策**：为什么采用某方案，是否仍有效。
- **待验证项**：设想、接线状态、未完成测试和环境假设。

旧《实现方案 v1.1》和旧 API 文档归入历史资料，不自动代表当前真实现状。当前仓库已有法师、共享玩家动画机、迷雾和救援代码，旧文档中的“两职业”“UpperBody”等描述不得作为新任务依据。

### 8.1 任务包质量规则

- “优化架构”“完善战斗”“做好 Boss”不是可执行目标。
- 验收不能只写“无报错”，必须列出操作、预期和边界条件。
- 重构必须列出不允许变化的现有行为。
- Unity 资产任务必须保护 GUID、公共字段、场景引用和动画状态名。
- 基线与任务包不符时先停止并报告，不根据旧聊天继续。

## 9. 可直接使用的提示模板

### 9.1 玩法讨论

```text
只讨论玩法，不写代码。围绕【目标】给出 3 个方案，分别说明：
玩家决策、队伍分工、与迷雾/撤离的关系、实现成本、规则漏洞和测试指标。
不得引入程序生成地牢、原创元素交互或专用服务器。
最后列出需要用户决定的 3 个问题，不替用户作最终决定。
```

### 9.2 编码执行

```text
先阅读 AGENTS.md、当前任务包及其中列出的文件，不做全仓扫描。
用不超过 8 行说明最小修改计划，然后严格执行任务包的文件边界和预算。
只进行一轮实现、指定测试和最多一轮修复；第二轮失败即停止。
不修改无关文件，不全量重写，不安装包，不同时做额外重构。
最后报告实际修改文件、真实测试结果、未执行测试、消耗和遗留问题。
```

### 9.3 行为保持型重构

```text
这是行为保持型重构。先列出现有公共入口、调用方和必须保持的行为。
保留资产 GUID、需要兼容的 public 字段、场景引用和动画状态名。
不得借重构新增职业、地图、Boss 招式或更换包版本。
超过任务文件上限或需要改变公共契约时停止，不自行扩大范围。
```

### 9.4 Unity 场景与预制体

```text
只处理任务包指定的场景或预制体。优先给出 Unity 操作步骤或可复查编辑器工具，
不要凭空生成大段 YAML。记录对象路径、组件、字段、引用来源和验收截图。
若实际层级与文档不一致，停止并报告，不通过复制对象“补齐”。
```

### 9.5 异构代码审查

```text
不要沿用实现者的结论，也不要重写方案。只根据任务包、提交差异和测试证据审查：
1. 是否完成目标且未越界；
2. 是否恢复 UpperBody、旧 Input、逐帧全场扫描等禁止方案；
3. 是否引入具体职业、UI、场景或网络反向依赖；
4. 是否可能破坏 GUID、动画状态、事件注销和对象池归还；
5. 验收证据是否足以支持完成。
按阻断/高/中/低列问题；无证据写“未验证”。
```

### 9.6 失败日志分析

```text
只根据以下错误日志和指定代码分析最可能的 3 个原因。
按“验证成本从低到高”给出检查步骤，不立即重写系统。
如果缺少信息，只列需要补充的最小文件或日志。
```

## 10. 完成定义（Definition of Done）

只有同时满足以下条件，任务才能标为完成：

1. 目标内修改完成，未超过文件和执行预算。
2. 指定编译与自动测试通过；未运行的测试明确记录。
3. Unity 手动验收有步骤和结果，关键路径有截图、日志或视频。
4. 无新增缺失脚本、关键空引用、重复事件订阅和对象池残留。
5. 数据 ID、GUID、公共字段和动画状态符合兼容要求。
6. 文档已同步，事实与规划没有混写。
7. 提交小而清晰，起始与最终提交被记录。
8. 成本记录已填写，遗留问题带严重级别和复现步骤。

“代码已生成”“理论上可运行”“Unity 打开没报错”均不等于完成。

## 11. 分支、提交与资产纪律

### 11.1 分支

- `main`：只保留已验收、可启动状态。
- `migration/unity-6-3`：只处理迁移。
- `feature/<system>-<short-name>`：单一功能。
- `refactor/<system>-<short-name>`：行为保持型重构。
- `docs/<topic>`：集中文档变更。
- 对照测试使用独立分支，不在主分支同时让多个代理修改同一任务。

### 11.2 提交

一个提交只做一件事。AI 可在验收后做本地提交；远端推送、发布和改写历史由用户决定。禁止在仓库中保存账号、密码、令牌、许可证文件或私人路径。

### 11.3 Unity 资产

- 场景、预制体、Animator Controller 指定唯一修改者，避免并行覆盖。
- 不在同一提交混合大规模场景调整与无关代码重构。
- 不通过文本替换批量猜改 GUID；移动资产保留 `.meta`。
- AI 不直接全量重写大型场景/控制器 YAML。
- 每次接线记录对象路径和字段，而不是只写“已拖好”。

## 12. 防回退硬约束

1. 目标版本为 Unity 6.3 LTS；旧 2022.3 仅作回退基线。
2. 玩家全员单层动画，弃用 UpperBody；普攻 `Attack_Draw → Attack_Release`。
3. 代码只设置动画触发器，不用 `Play()` 硬切作主路径；Any State 仅限必要的受击/死亡打断，禁止自过渡。
4. 使用 `PlayerBase + Override` 和同构敌人共享控制器；Animator 位于模型子节点，Culling 为 Always Animate。
5. 命中以 `normalizedTime` 比例窗口为主、代码时钟回退，不用 AnimationEvent 作主命中路径。
6. 攻速单一数据源；新增动作不得另建互相矛盾的攻速管线。
7. 伤害走统一上下文和结算入口；表现只订阅结果。
8. 新功能不得恢复逐帧 `FindObjectsByType` 全场扫描；使用单位注册和低频感知。
9. 新交互不得直接读取选择器、输入和具体 UI；走统一交互契约。
10. 新技能效果不得直接依赖 `SwordSwing`、`MonsterBrain` 或 `GameData`。
11. 新楼层不得硬编码传送和复制流程；使用楼层定义、入口/出口和落点。
12. 客户端不可见不得停掉房主权威 AI 模拟。
13. 数据目录目标为 `Data`；移动必须保留 GUID，不恢复 `Date` 新资产。
14. 不引入 DOTS/ECS、程序生成地牢、专用服务器、深度学习或无关大型框架。

改变上述任一项前必须写 ADR，说明新证据、影响和迁移方案。

## 16. 审查清单

### 代码与测试

依赖方向、静态状态、全场扫描、事件注销、对象池重置、具体职业/UI 反向依赖、重复结算、网络权威、空引用和真实测试证据。

### Unity 资产

GUID、Missing Script、Prefab Variant 覆盖、Animator 状态/参数、材质实例、碰撞与遮挡、NavMesh、重复管理器和网络预制体登记。

### 协作与成本

任务是否越界、是否触发第二轮以上无效修复、是否消耗异常、是否由异构模型审查高风险差异、人工修复是否记录。

### 文档

事实/历史/待验证是否分开；版本是否真实；完成项是否有证据；旧方案是否复活；交接是否指向下一步。

## 17. 安全与边界

- 公开仓库只用于无需登录的只读共享；不要发送账号、密码、访问令牌或许可证破解文件。
- 压缩包只包含 `Assets`、`Packages`、`ProjectSettings` 及必要文档，排除 `Library`、`Temp`、`Logs`、`obj` 等生成目录。
- AI 默认只读审查和本地工作，不向远端推送、不发布版本、不删除分支。
- 不使用来路不明的授权补丁、DLL 或绕过许可证的工具。
