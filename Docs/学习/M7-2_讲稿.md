# M7-2 学习讲稿：消除 11 条上行边

> 风险等级：高风险（改暂停/升级/模态/门过场运行时行为）
> 工单：`Docs/交接/TASK_M7-2_消除上行边.md`
> 报告：`Docs/交接/REPORT_M7-2_消除上行边.md`

## 0. 一句话

把 Gameplay 对 App/UI 的 11 条引用，改成 Gameplay 自己的“状态 / 接口 / 事件”下沉点，让 `upward_layer_edges` 从 11 归零，同时暂停、升级、背包模态、地牢门过场的行为逐项等价。

## 1. 原问题：11 条边是怎么来的

- 迁移完成后目录已是“Core ← Content ← Gameplay ← App ← UI”，但代码里还有 11 条反向引用：
  - `MeleeCombat` 读 `MetaState.Level`（Gameplay→App）；
  - 7 处 AI/输入/救援读 `AppFlow.IsPaused`（Gameplay→App）；
  - 2 处输入读 `UIManager.instance.IsInventoryOpen`（Gameplay→UI）；
  - `DungeonDoor` 直接调 `TransitionFader.Transition`（Gameplay→UI）。
- 这些引用让 M7-3 无法给 Gameplay 建 asmdef：一旦 Gameplay 程序集不引用 App/UI，这 11 处会立刻编译失败。
- 关键判断：**不是把 App/UI 下沉到 Gameplay**（会造成 UI→Gameplay→UI 环），而是把“Gameplay 需要的状态/契约”下沉到 Core/Gameplay，让 App/UI 反过来依赖它们。

## 2. 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 把 `AppFlow`/`UIManager`/`TransitionFader` 整体移到 Gameplay | 改动最小 | App/UI 分层消失；UI→Gameplay→UI 成环；M7-3 必炸 | 弃用 |
| B | **下沉状态/接口/事件**：`ProgressionState`、`PauseState`、`IUiModalState`、`TransitionRequest` | 依赖单向；每步可自动断言；回滚粒度细 | 4 个子项、4 次套件 | **选定** |
| C | 反射/服务定位器绕开编译期引用 | 不改调用点 | 隐藏依赖，asmdef 无法约束 | 弃用 |

## 5. 设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| AppFlow.IsPaused 是否删 | **保留为转发** | `PauseManager`/`EscMenuPanel` 还在用；D9 旧适配层 M7 内不删 |
| MetaState.Level 是否删 | **保留为转发** | `GameData`/`HUD` 在用；删了会扩大改动面 |
| 暂停是否用事件 | **用静态状态** | 暂停是“每帧读的布尔”，事件会引入订阅时序与丢失风险；状态更简单 |
| 模态是否用事件 | **用接口 + 注册表** | 输入每帧读；接口 `Current` 一次注册，未注册时安全返回 |
| 门是否用接口 | **用事件** | 过场是一次性触发 + 异步协程；事件解耦最自然 |
| 新类型放哪 | Core 2 / Gameplay 根 1 / World 1 | 严格遵守“目录 = 命名空间 = asmdef 边界”；App/UI 不许放 |
| 测试断言放哪 | REFACTOR 第 17–20 条 | 复用既有 red/green 与 Summary 机制，不新建套件 |

## 6. 边界与失败模式

| 失败模式 | 症状 | 防线 |
|---|---|---|
| 升级收益改错 | 金币/等级/伤害倍率与基线不一致 | `Refactor.ProgressionFacade` 断言 +1 级/金币归 0/等级转发 |
| 暂停把团灭当暂停 | 团灭后按 Esc 逻辑异常 | `Refactor.PauseFacade` 断言 `timeScale=0` 时 `IsPaused=false` |
| `timeScale` 多入口 | 暂停恢复后时间仍为 0 | `PauseState` 不写 `timeScale`；`AppFlow`/`RunFlow` 写入口不变 |
| 模态注册时序 | Gameplay 早于 `Awake` 读导致空引用 | `Current != null` 判空；`UIManager.Awake` 注册 |
| 事件重复订阅 | 一次过场播两次 | `OnEnable/OnDisable` 成对订阅/退订；断言只发布一次 |
| 门场景无对象 | 断言 blocked | 运行期 fader 夹具（结束销毁），与既有 `REFACTOR_Target_*` 同惯例 |
| 冒烟漏行为 | 暂停/背包/门异常 | Play 30s 冒烟 + 所有者 3 项目检 |

## 7. 答辩 Q&A（5 条）

**Q1：为什么 `PauseState` 不直接管 `timeScale`？**
A：`timeScale` 有两个合法写入口：Esc 暂停（AppFlow）和团灭（RunFlow）。如果把 `timeScale` 塞进 `PauseState`，团灭也会被误标成“暂停”，恢复逻辑会把团灭时间轴拉回 1。现在 `PauseState` 只存“Esc 暂停”语义，`timeScale` 仍由原入口写，两者解耦。

**Q2：`MetaState.Level` 都转发了，为什么不干脆删掉？**
A：`GameData.level` 和 `HUD` 还在读 `MetaState.Level`；D9 明确旧适配层 M7 内保留。转发属性让旧调用点零改动，同时把真实存储下沉 Core，M7-3 建 asmdef 后 App→Core 是合法方向。

**Q3：`IUiModalState` 为什么不用 `IsAnyPanelOpen`？**
A：现有行为只屏蔽“背包打开”时的右键/技能；`IsAnyPanelOpen` 会把 Esc 菜单、属性面板也算进去，行为会变。D6 要求严格等价，所以 `IsModalOpen => IsInventoryOpen`。

**Q4：`TransitionFader` 在 `OnEnable` 订阅，场景重载会不会重复？**
A：Unity 保证 `OnEnable`/`OnDisable` 成对；`EventBus.Unsubscribe` 用 `Delegate.Remove`，重载时旧实例在 `OnDisable` 退订，新实例再订阅。测试里也显式 `Unsubscribe` 临时 handler。

**Q5：为什么断言能证明行为不变，而不是只证明“能跑”？**
A：每条断言都走生产入口并检查数值/状态：升级检查等级与金币、暂停检查 `timeScale` 与 `IsPaused` 的双向、模态检查 `IsModalOpen == IsInventoryOpen`、门检查事件送达 + alpha 峰值/归零。再加上 `SPEC01` 12 条既有行为口径与 `FND00B06` 12/0+2obs，行为等价有多层证据。

## 8. 三句话总结

1. 跨层依赖优先下沉“状态/接口/事件”，不要下沉整个类。
2. `timeScale` 是物理时间轴，`IsPaused` 是玩家意图，两者必须解耦。
3. 每条重构断言先红后绿，回滚锚就是每个子项的 commit。
