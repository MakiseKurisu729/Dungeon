# M7-3 学习讲稿：建 Gameplay / App / UI / Editor 程序集

> 风险等级：高风险（程序集边界 = 编译单元；MonoBehaviour GUID 引用面）
> 工单：`Docs/交接/TASK_M7-3_建程序集.md`
> 报告：`Docs/交接/REPORT_M7-3_建程序集.md`

## 0. 一句话

给 `Gameplay`/`App`/`UI`/`Editor` 四个目录各加一个 asmdef，用 `references` 把 `Core ← Content ← Gameplay ← App ← UI` 钉进编译期，Editor 只参与编辑器编译；**零代码改动**，套件与 Play 冒烟保持基线。

## 1. 原问题：目录归一了，但边界还是“软”的

- M7-1/M7-2 完成后目录、命名空间、依赖方向都对了，但所有脚本仍是两个预定义程序集（`Assembly-CSharp` / `Assembly-CSharp-Editor`）。
- 只要不是 asmdef，`Gameplay` 里的代码仍然可以偷偷 `using Dungeon.App` 或 `using Dungeon.UI`——编译器不会拦。
- M7-3 的目标就是把这层“软约定”变成“编译期硬约束”：一旦反向引用，直接 CS0246。

## 2. 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 一次性建 4 个 asmdef | 提交少 | 一次编译红面覆盖全仓，难定位；循环引用难查 | 弃用 |
| B | **逐个建**：Gameplay → App → UI → Editor，每步跑套件 | 每步可编译可回滚；循环引用在对应步暴露 | 4 次编译 + 4 次套件 | **选定**（D15） |
| C | 先建 UI/App 再建 Gameplay | — | 下层未固化，上层引用反复改 | 弃用 |

## 3. 数据流（编译期）

```text
目录 → asmdef → 编译器切程序集 → references 决定可见性
Scripts/Core      → Dungeon.Core      refs []
Scripts/Content   → Dungeon.Content   refs [Core]
Scripts/Gameplay  → Dungeon.Gameplay  refs [Core, Content, UnityEngine.UI]
Scripts/App       → Dungeon.App       refs [Core, Content, Gameplay]
Scripts/UI        → Dungeon.UI        refs [Core, Content, Gameplay, App, UnityEngine.UI]
Scripts/Editor    → Dungeon.Editor    refs 全部运行时 + includePlatforms [Editor]
Assets/_Project/Tests → Assembly-CSharp(.Editor)，靠 autoReferenced 自动看见全部
```

运行时行为不变：程序集只是编译边界，不改类型布局、字段名、GUID。

## 4. 关键代码位置（5 处）

1. `Assets/_Project/Scripts/Gameplay/Dungeon.Gameplay.asmdef:4`
   `"references": ["Dungeon.Core", "Dungeon.Content", "UnityEngine.UI"]` —— 最大的一层，先把它的可见范围定死。
2. `Assets/_Project/Scripts/App/Dungeon.App.asmdef:4`
   `"references": ["Dungeon.Core", "Dungeon.Content", "Dungeon.Gameplay"]` —— App 不能看到 UI。
3. `Assets/_Project/Scripts/UI/Dungeon.UI.asmdef:4`
   `"references": ["Dungeon.Core", "Dungeon.Content", "Dungeon.Gameplay", "Dungeon.App", "UnityEngine.UI"]` —— 顶层可以看全部下层。
4. `Assets/_Project/Scripts/Editor/Dungeon.Editor.asmdef:5`
   `"includePlatforms": ["Editor"]` —— 只参与编辑器编译，不进 player build。
5. `Docs/QA/Evidence/M7-3/verify_m7_3.py:38-44`
   `SPECS` 表：6 个 asmdef 的期望字段集中定义，`--stage 1..4` 逐步校验；`:96` 起校验 EditorOnly。

## 5. 设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 是否先建 Core/Content | 已在 M7-1 批 3 后建好 | 叶层先固化，M7-3 只补上层 |
| `autoReferenced` | **true** | 30 个测试在预定义程序集，必须自动引用全部 asmdef，否则测试全红 |
| `noEngineReferences` | **false** | 需要 UnityEngine/UnityEngine.AI 等引擎模块 |
| Gameplay 是否引 uGUI | **引 `UnityEngine.UI`** | `DamageNumber`/`WorldHealthBar` 直接用 `Text/CanvasScaler/Image` |
| UI 是否引 uGUI | **引 `UnityEngine.UI`** | 面板/HUD/背包/技能栏/EventSystems |
| Editor 是否单独 asmdef | **是，`includePlatforms:["Editor"]`** | 运行时程序集不应回引 Editor；player build 不应包含它 |
| 测试是否建 asmdef | **不建**（M7-3 范围外） | D8/TEST-03 再处理；`autoReferenced` 已保证能编译 |
| 引用是 name 还是 GUID | **name** | 与 TASK §2.1 一致；asmdef 支持名称引用，重命名程序集时更直观 |

## 6. 边界与失败模式

| 失败模式 | 症状 | 防线 |
|---|---|---|
| 缺 uGUI 引用 | CS0246 `Text/Image/CanvasScaler` | Gameplay/UI 都显式引 `UnityEngine.UI` |
| 循环引用 | CS0234 / “circular reference” | 逐层建；每步编译 0 error 才继续；2 轮不解决就回退该 asmdef 并停 |
| 运行时回引 Editor | 编译通过但架构错 | `verify` 的 EditorOnly 断言；`editor-only.txt` |
| Editor 进 player build | 打包多出编辑器代码 | `includePlatforms:["Editor"]` |
| 测试编译失败 | `Tests/**` CS0246 | 6 个 asmdef 全部 `autoReferenced=true` |
| 场景 Missing Script | Play 冒烟报错 | asmdef 不改 GUID；UI/Editor 步各跑 30 秒冒烟 |

## 7. 答辩 Q&A（5 条）

**Q1：为什么 Gameplay 必须引用 `UnityEngine.UI`，而不是把 UI 代码移走？**
A：`DamageNumber` 的飘字用 `Text/CanvasScaler`、`WorldHealthBar` 用 `Image`，这些是 Gameplay 的表现层组件。M7-3 只建程序集、不改代码，所以正确做法是让 Gameplay 引用 uGUI；把 UI 移走属于重构，超出本单范围。

**Q2：`autoReferenced=true` 会不会让边界失效？**
A：不会。`autoReferenced` 只影响“预定义程序集是否自动引用该 asmdef”，不改变 asmdef 自己声明了哪些 `references`。边界仍由每个 asmdef 的 `references` 决定；测试是预定义程序集，所以必须 true。

**Q3：Editor 程序集为什么不能放进 `Assembly-CSharp-Editor` 就行？**
A：`Scripts/Editor/` 默认就进 `Assembly-CSharp-Editor`，但那样没有显式的程序集名，其他 asmdef 无法引用它、也无法在 asmdef 层面保证“不进 player build”。独立 `Dungeon.Editor` + `includePlatforms:["Editor"]` 把这两个约束显式化。

**Q4：程序集边界会不会影响场景里的 MonoBehaviour 引用？**
A：不会。场景/预制体保存的是脚本 GUID，asmdef 只改变编译单元，不改变 `.cs.meta` 的 GUID；UI/Editor 两步的 Play 冒烟都没有 `Missing script`。

**Q5：为什么每步都要跑 REFACTOR/SPEC01，而不是最后跑一次？**
A：程序集是“全局开关”：任何一步的 references 写错都可能让整个编译红。逐层跑可以在错误刚出现时就定位到具体层；同时每步一条 commit 就是一条独立回滚锚。

## 8. 三句话总结

1. asmdef 不是“加个文件”，而是把架构不变量写进编译器。
2. `includePlatforms` 决定“能不能进包”，`references` 决定“能不能看见”，两者缺一不可。
3. 先叶后根、逐层验证，是程序集拆分唯一稳的顺序。
