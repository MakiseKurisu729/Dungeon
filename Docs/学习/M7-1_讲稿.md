# M7-1 学习讲稿：目录与命名空间归一

> 风险等级：高风险（60 文件迁移、`.meta`/GUID 面）
> 任务：`Docs/交接/TASK_M7-1_目录与命名空间归一.md`
> 报告：`Docs/交接/REPORT_M7-1_目录与命名空间归一.md`

## 0. 一句话

把 77 个脚本从“按功能随手放”的旧目录，迁移成“目录 = 命名空间 = 未来 asmdef 边界”的六层结构，并在 Core/Content 上先建程序集护栏；全程零逻辑改动、GUID 不断、四套回归保持基线。

## 1. 原问题：为什么非迁不可

- 迁移前 77 个脚本散在 `Core/Units/Combat/Items/Player/System/Debug/Framework/UI/Gameplay/Interaction`，目录名与职责不一致（例如 `System/` 里是宝箱和门，`Core/UnitRegistry` 却依赖玩法类型）。
- 所有类型都在**全局命名空间**：无法按程序集切分，任何“Core 不许依赖玩法”的规则只能靠口头约定；M7-0 审计发现 533 条边里有 **11 条上行边**（Gameplay→App/UI），但连“谁是下层”都无法在编译期表达。
- asmdef 的硬性前提是**程序集边界 = 目录边界**；不先做目录/命名空间归一，M7-2/M7-3 每建一个 asmdef 都要再挪一次文件，返工不可避免。

## 2. 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 一次性移动 77 文件 + 一次性加命名空间，最后统一修编译 | 提交少 | 一次编译红面覆盖全仓，出错无法定位；回滚粒度=全部 | 弃用 |
| B | **4 批按目标层**：Core+Content → Gameplay → App → UI/Editor；批 3 后建 Core/Content asmdef | 每批独立可编译/可回滚；叶层先固化，上层只改引用方 | 提交多、测试 using 要按批补 | **选定**（D1） |
| C | 只加命名空间不动目录，asmdef 用 `name` 硬指目录 | 迁移量小 | 违反“asmdef 边界=目录边界”，M7-3 必然返工 | 弃用 |

选择 B 的核心判断：**编译红面必须被限制在一层内**。批 1 只碰 Core/Content，批 2 只碰 Gameplay，批 3 只碰 App，批 4 只碰 UI/Editor；任何一批失败都能独立 `git revert`，不影响其他层。

## 3. 数据流

```text
源码磁盘路径
  └─(成对移动 .cs + .cs.meta)→ Unity 资产库（GUID 不变）
        └─(目录内 asmdef)→ 编译器切程序集
              ├─ Dungeon.Core       （7 文件，不引用项目内其他类型）
              ├─ Dungeon.Content    （3 文件，只引 Core）
              └─ Assembly-CSharp    （Gameplay/App/UI/Editor 暂未建 asmdef）
        └─(using 解析)→ 运行时类型绑定不变 → 行为零变化
```

- 测试仍在预定义程序集（无 asmdef），`autoReferenced=true` 让它自动引用 Core/Content；测试只补 `using`，不改断言。
- 场景/预制体通过 GUID 找脚本；`.meta` 跟着 `.cs` 走，场景序列化数据一个字节都不用改。

## 4. 关键代码位置（5 处）

1. `Assets/_Project/Scripts/Core/MessageFeed.cs:16`
   `public static void RaiseChanged() { Changed?.Invoke(); }` —— 唯一的可见性改动（`internal`→`public`）。因为 `MessageFeed` 进 `Dungeon.Core` 程序集后，`Dungeon.App` 的 `GameData` 适配层要调用它，`internal` 会跨程序集编译失败（D17）。
2. `Assets/_Project/Scripts/Content/UnitStats.cs:2-3`
   `using Dungeon.Core;` + `namespace Dungeon.Content {` —— Content 依赖 Core 的最小例子：`UnitStats.team` 字段类型是 `Dungeon.Core.Team`。
3. `Assets/_Project/Scripts/Gameplay/Combat/MeleeCombat.cs:3-7`
   `using Dungeon.Content; using Dungeon.Core; using Dungeon.Gameplay.Units; using Dungeon.App; namespace Dungeon.Gameplay.Combat {` —— 一行 `using` = 一条依赖边；其中 `using Dungeon.App` 就是审计里的那条 **Gameplay→App 上行边**（`MetaState.Level`），M7-2 必须消掉。
4. `Assets/_Project/Scripts/UI/UIManager.cs:7`
   `namespace Dungeon.UI {` —— UI 原地加命名空间；UI 是“只被上层看、不反向依赖”的顶层，M7-3 建 asmdef 时只需要加 `UnityEngine.UI` 引用。
5. `Assets/_Project/Scripts/Core/Dungeon.Core.asmdef:2-4`
   `"name": "Dungeon.Core"` + `"rootNamespace": "Dungeon.Core"` + `"references": []` —— 空的 `references` 是硬护栏：Core 一旦 `using` 任何项目内其他命名空间，编译立刻红。
6. （验证侧）`Docs/QA/Evidence/M7-1/verify_m7_1.py:265`
   `# ---------------- M7-1.Structure.Meta` —— 对每个移动文件比对基线 `.meta` 的 `guid:`，这是“GUID 不断”的自动化证据。

## 5. 设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 命名空间风格 | `Dungeon.<Layer>[.<Sub>]` | 与 asmdef 名一一对应；`rootNamespace` 直接复用，IDE 新建文件自动带 namespace |
| 块级 vs 文件级 namespace | **块级** | Unity 2022.3 的 C# 9 不支持文件级 namespace（C# 10 才有） |
| 是否先加 asmdef 再迁移 | **先迁移、批 3 后才建 Core/Content** | 迁移期间全局命名空间不会因 asmdef 缺失而无法引用；先建 asmdef 会把“未迁完的 Core 目录”错误地锁成程序集 |
| `.meta` 移动方式 | 文件系统成对移动 + `refresh_unity` | MCP `manage_asset move` 实际成功但返回失败；`git mv` 被禁；成对移动可逐字节校验 `.meta` 不变 |
| 测试是否加 namespace | **不加** | 测试目录没有 asmdef，加 namespace 只会增加 `using` 噪声；M7-4/TEST-03 再统一 |
| 旧适配层 | 保留 `GameData`/`GameFlow`/`PauseManager` | D9：删除涉及场景/预制体，另开单由所有者操作 |
| 旧空目录 | 保留 | 不在工单授权文件清单；`Framework`/`Monster` 由大脑明确“不要删” |

## 6. 边界与失败模式

| 失败模式 | 症状 | 本任务的防线 |
|---|---|---|
| `.meta` 丢失 / GUID 断裂 | 场景 `Missing script`、`.meta` 删除+新增配对 | 成对移动 + `M7-1.Structure.Meta` 的 `guid_bad` + 批 2/4 Play 冒烟 |
| 命名空间漏加/错层 | `error CS0246`/`CS0234` | `verify` 每文件 namespace 断言 + 编译 0 error 门槛 |
| 顺手改逻辑 | `git diff -w` 出现非 namespace/using 行 | 逐文件正文归一化比对 + 提交后 `git diff -w` 扫描 `offenders=0` |
| Core 不纯（引用 Gameplay） | `Dungeon.Core` 程序集编译红 | Core asmdef `references=[]` 硬护栏；审计 `Core→非Core` 边 0 |
| 测试没跟上 | `error CS` 出现在 `Tests/**` | 每批按编译错误补 `using`；测试保持 30 文件无 namespace |
| 暂停/升级等行为变化 | `REFACTOR`/`SPEC01` 红 | 本任务零逻辑改动 → 任何套件红都按 revert 处理 |
| git rename 误判 | `git diff` 把 `RunFlow.cs` 配给 `AppFlow.cs` | 不依赖 `.cs` rename 展示；用 60 个 `.cs.meta` 100% rename + 路径集合 + GUID 三项独立证明 |

## 7. 答辩 Q&A（5 条）

**Q1：为什么不能一次性移动 77 个文件？**
A：一次性移动后，任何一处 `using` 漏补都会让整个程序集编译失败，错误列表跨 10 个目录，定位成本高且无法按层回滚。分批后每批的编译红面只在一层内，失败时 `git revert` 一条提交即可回到上一个可编译状态。

**Q2：`.meta` 和 GUID 到底是什么关系？移动文件为什么不会断引用？**
A：Unity 用 `.meta` 里的 `guid:` 作为资产的稳定 ID；场景/预制体保存的是 GUID 而不是路径。只要 `.cs` 和 `.cs.meta` 一起移动、`.meta` 内容不变，GUID 就不变，场景引用自然不断。本任务用 60 个 `.cs.meta` 100% rename + `verify` 的 `guid_bad=[]` 两项证明。

**Q3：命名空间改了，为什么运行时行为能保证不变？**
A：命名空间只影响编译期的类型全名解析，不改变类型布局、字段名、方法体、序列化字段名。`Cooldown` 是普通 struct 字段，字段名不变；`UnitStats`/`WeaponData`/`ItemData` 是 ScriptableObject，靠 GUID 引用。加上 `REFACTOR 16/0`、`SPEC01 12/0` 和两次 Play 冒烟，行为等价有自动化证据。

**Q4：`MessageFeed.RaiseChanged` 为什么必须改 `public`？**
A：批 3 后 `MessageFeed` 在 `Dungeon.Core` 程序集，`GameData` 在 `Dungeon.App` 程序集。`Dungeon.App` 引用 `Dungeon.Core`，但 `internal` 成员对另一个程序集不可见，`GameData.AddGold/TryLevelUp` 调用 `RaiseChanged` 会编译失败。改成 `public` 是 D17 的最小改动，方法体与签名其余部分不变。

**Q5：为什么 Core 的 asmdef 能证明“Core 不依赖玩法”？**
A：asmdef 的 `references=[]` 表示 `Dungeon.Core` 不引用任何项目内程序集（只引用引擎）。如果 Core 里出现 `using Dungeon.Gameplay.*` 或直接引用 `UnitHealth`，编译器会报 CS0246/CS0234，构建直接红。这比人工 review 更硬；审计侧再用 `edges.csv` 的 `src_layer=Core` 且 `dst_layer≠Core` = 0 做双重确认。

## 8. 三句话总结（背这两句就够）

1. 目录决定程序集边界，命名空间决定编译期可见性；两者一致，asmdef 才有意义。
2. `.meta` 跟 `.cs` 走，GUID 不变，场景就不会 Missing；这是迁移安全的底线。
3. 每批一个可编译、可回滚的提交，比一次做完再修更便宜。
