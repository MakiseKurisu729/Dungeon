# 魔石地牢：总体架构与内容生产规范

> 文档版本：v1.0（设计基线）  
> 编制日期：2026-11-01  
> 适用项目：Unity 3D 俯视角 RTS 式多单位操控、2～4 人 P2P 合作“搜打撤”地牢探索游戏  
> 事实基线：公开仓库 `MakiseKurisu729/Dungeon`，提交 `e1e197dca373636a130c161b73246d8a373acc7f`  
> 当前工程：Unity 中国版 `2022.3.62f3c1`；目标工程：Unity 6.3 LTS  
> 本文性质：后续实施规范，不代表目标系统已经完成。

## 0. 状态标记与阅读规则

- **【现有】**：仓库中已有代码或资产，但不等于已经完成最终验收。
- **【重构】**：已有可复用基础，需要调整职责、依赖或数据格式。
- **【新增】**：仓库当前没有，需要后续实现。
- **【待验证】**：设计建议或迁移假设，必须在 Unity 6.3 中实测后冻结。
- **【暂缓】**：不进入本次毕业设计关键路径。

冲突时按以下顺序处理：当前任务书与硬约束 > 本文目标架构 > 仓库实际行为 > 旧《实现方案》与旧 API 文档。旧文档中的“已完成”只能作为历史记录，不能替代当前验收。

## 1. 架构总决策

### 1.1 项目目标

形成一款完整可演示的原型：整备编队 → 进入三层主题化地牢 → 在共享战争迷雾中探索、战斗和搜集 → 通过固定激活式双向撤离点撤离 → 队伍与城镇成长 → 挑战两类多阶段首领。最多 4 个玩家单位，支持 2～4 人 P2P 合作，不使用专用服务器。

### 1.2 技术路线

1. 采用**模块化单工程、组件化 GameObject、数据驱动内容**，不迁移 DOTS/ECS。
2. 采用**薄核心、厚内容、可替换适配器**：战斗、交互、AI 和场景注册提供稳定契约；职业、怪物、楼层和界面通过数据及组合扩展。
3. 保留现有有效模式：ScriptableObject、技能策略、`DamageInfo`、同域 C# 事件、跨域事件、`SimplePool`、`ICharacterCombat`、Animator Override、比例命中窗口。
4. 优先消除会阻碍内容扩展的耦合：静态全局状态、逐帧全场扫描、技能直调具体职业、Boss 直调场景奖励、交互各自处理输入和 UI。
5. 联机属于外层适配和工程验收，不作为研究主线；但指令、状态和场景切换从早期就避免只能单机调用的写法。
6. 三层地牢全部手工或模块化搭建，不开发程序生成地牢，不开发攻城战，不实现原创元素交互，不使用深度学习或神经网络。

### 1.3 可扩展性的验收定义

“可扩展”不是类数量多，而是新增内容时的修改范围可控：

- 新增一个普通职业，不修改选择、输入、伤害、HUD、存档和联机核心；只有出现全新机制时才增加对应效果执行器。
- 新增一种同构敌人，不复制 `MonsterBrain`；通过数值、感知、动作和动画 Override 组合完成。
- 新增一层地牢，不修改 `GameFlow`、迷雾、撤离或场景加载核心；只增加场景、楼层定义、区域图和内容配置。
- 新增一个首领阶段，不把条件继续堆进 `BossBrain.Update()`；由阶段、动作、场地和事件组件组合完成。
- 新增一种交互物，不修改 `SelectionManager`；实现统一交互目标契约并配置距离、耗时、条件与结果。

### 1.4 架构不变量（2026-11-05 自归档文档 `03` §12 接手）

改变下列任一项前**必须先写 ADR**（说明新证据、影响与迁移方案），否则不得修改。

1. 目标版本 Unity 6.3 LTS；Unity 2022.3 只作回退基线。
2. 玩家全员单层动画，弃用 UpperBody；普攻 `Attack_Draw → Attack_Release`（远程普攻在 `AttackRange` 子状态机内保持该顺序）。
3. 代码只设置动画触发器，不用 `Play()` 硬切作主路径；Any State 仅限受击/死亡等确需全局打断的状态（技能槽自 ADR-0003 起例外，见本节末），禁止自过渡。
4. 使用 `PlayerBase + Override`，同构敌人共享控制器；Animator 位于模型子节点，Culling 为 Always Animate。
5. 命中以 `normalizedTime` 比例窗口为主、代码时钟回退，不用 AnimationEvent 作主命中路径。
6. 攻速单一数据源（`UnitStats.attackSpeed`）；新增动作不得另建互相矛盾的攻速管线。
7. 伤害走统一上下文与结算入口；表现只订阅结果。
8. 不恢复逐帧 `FindObjectsByType` 全场扫描；用单位注册与低频感知。
9. 新交互不得直接读取选择器、输入和具体 UI；走统一交互契约。
10. 新技能效果不得直接依赖 `SwordSwing`、`MonsterBrain`、`GameData`。
11. 新楼层不得硬编码传送与复制流程；使用楼层定义、入口/出口和落点。
12. 客户端不可见不得停掉房主权威 AI 模拟。
13. 数据目录目标为 `Data`；移动必须保留 GUID，不恢复 `Date` 新资产。
14. 不引入 DOTS/ECS、程序生成地牢、专用服务器、深度学习或无关大型框架。

动画相关例外（2026-11-05，依据 `Docs/Decisions/ADR-0003_技能动画槽位化与子状态机.md`）：

- 技能槽 Q/W/E/R 为子状态机（每段一状态一 Clip，支持多段技能），允许 `AnyState → 槽` 打断普攻、`Has Exit Time = 0`。
- 远程普攻 `AttackRange` 为子状态机（`Draw → Release`），不烘 Clip。
- 覆盖器按“槽的段”覆盖 Clip；运行时换技能按槽换整组 Clip。
- 除技能槽外，Any State 仍只限受击/死亡。

### 2.2 已确认的主要债务

| 位置 | 当前问题 | 目标改造 |
|---|---|---|
| `SkillSystem` / `SkillEffectBase` | 效果依赖具体 `SkillSystem`，后者又持有 `SwordSwing` | 引入施法上下文和能力接口，效果不再识别具体职业执行器 |

| `UnitBrain` / `MonsterBrain` / `BossBrain` | 感知、决策、移动、攻击和场景奖励混合，且重复全场扫描 | 感知查询、指令执行、AI 决策、遭遇编排分离 |
| `GameData` / `GameFlow` | 静态局内数据与静态流程状态，跨场景语义不清 | 明确应用、局内、楼层和单位四级生命周期 |
| `Interactable` / `Chest` / `DownedRescue` / `DungeonDoor` | 三套交互路径，部分目标自己读输入、选人和 UI | 统一指令、条件、读条、打断和结果；表现订阅结果 |

| `UIManager` | 同时掌握多个具体面板和玩法对象 | 保留 UI 咽喉，但逐步改为面板注册和视图模型绑定 |

## 3. 目标代码架构

### 3.1 分层与依赖方向

```text
Core（ID、命令、结果、事件、时间、通用接口）
  ↑
Content（ScriptableObject 内容定义，不保存局内运行状态）
  ↑
Gameplay（单位、战斗、交互、AI、迷雾、楼层运行）
  ↑
App（局流程、整备、撤离、成长、存档、服务定位）
  ↑                         ↑
UI（面板与视图模型）      Net（NGO 适配、RPC、网络状态）

Editor / Tests 只依赖上述层，不允许运行时代码反向依赖 Editor。
```

规则：

1. 下层不得引用上层具体类型；表现、UI 和联机不能成为战斗结算的前置条件。
2. 内容资产可以引用其他内容资产，不持有场景对象和局内血量、冷却等运行数据。
3. 同域内使用直接方法或 C# 事件；跨域只发布有明确所有者的领域事件。事件不是替代所有调用的理由。
4. 场景对象通过组合根显式接线；只允许编辑器引导和小范围自动查找，禁止用连续全场扫描代替依赖关系。
5. 先建立命名空间和目录边界，依赖稳定后再加 `asmdef`。禁止为了“分层好看”制造循环引用。

### 3.3 程序集策略

【新增，待重构后实施】初期只建议以下边界：

- `Dungeon.Core`：尽量纯 C#，不引用 UI、Net 或 Editor。
- `Dungeon.Content`：内容定义，引用 Core。
- `Dungeon.Gameplay`：运行时玩法，引用 Core、Content。
- `Dungeon.App`：流程、成长、存档与组合根，引用 Gameplay。
- `Dungeon.UI`、`Dungeon.Net`：外层适配，按需引用 App 的公开契约。
- `Dungeon.Editor`：编辑器工具；`Dungeon.Tests.*`：测试。

若现有依赖尚未清理，不要立即拆出十多个程序集。先让一个 `Gameplay` 程序集内部的命名空间遵守边界，再按实际依赖拆分。

## 4. 核心运行机制

### 4.1 生命周期与服务边界

| 生命周期 | 内容 | 进入/退出规则 |
|---|---|---|
| 应用级 | 设置、内容索引、存档、网络会话、场景加载 | 应用启动创建，退出释放；不随楼层重载重置 |
| 局内级 | 本次探索的队伍、资源、战利品、撤离状态、统计 | 进入探索创建，成功/失败结算后释放 |
| 楼层级 | 区域图、单位注册、迷雾、遭遇、场地状态 | 楼层加载创建，跨层卸载释放 |
| 单位级 | 血量、资源、冷却、状态、AI、动画 | 生成注册，销毁或回收注销 |

【重构】`GameData` 不再同时承担金币、成长、消息和职业数值修改。拆为局内状态、成长状态与消息事件；禁止用 `static` 字段隐式跨场景保留所有数据。

### 4.2 单位注册与查询

【新增】`UnitRegistry` 是楼层级服务，保存单位 ID、队伍、楼层、存活状态、查询接口和空间索引。`UnitHealth`、`UnitBrain`、迷雾、救援、目标选择和团灭判定都使用它，不再各自 `FindObjectsByType`。

- 单位生成/启用时注册，销毁/回收/跨层时注销。
- 查询分队伍、楼层、范围和状态；高频范围查询使用均匀网格等简单空间索引。
- AI 感知以固定低频更新并分帧，移动和动画表现仍逐帧更新。
- 事件只通知变化，范围查询由注册表提供；不要每帧广播所有单位快照。

### 4.3 事件规范

【保留＋重构】现有 `EventBus` 可作为起点，但必须补充：

- 事件名称使用过去式，如 `DamageResolved`、`UnitDowned`、`ExtractionCompleted`。
- 每种事件注明发布者、订阅者、时机和是否允许重入。
- 订阅与注销成对出现，楼层/局内事件不得泄漏到下一局。
- 关键结算优先同步、有序执行；跨域通知不能改变已经结算的结果。
- 不用全局字符串消息驱动玩法逻辑；文本提示只订阅结果事件。

### 4.4 统一交互

【重构】保留“点击目标 → 选中单位接近 → 满足条件 → 执行”的 RTS 操作方式，统一为：

```text
Interactable（场景身份与提示）
  + InteractionDefinition（距离、耗时、移动需求、打断规则）
  + IInteractionTarget（条件检查、开始、完成、取消）
  + InteractionRunner（单位侧读条和状态）
```

宝箱、救援、门、撤离点、机关只实现自身条件和结果，不读取 `Input`、不查找 `SelectionManager`、不直接打开具体 UI。UI 根据交互状态显示读条和结果。

必须定义并发规则：同一目标允许几个交互者、谁先占用、取消是否返还、联机下由谁裁决、目标死亡或跨层如何终止。

## 5. 战斗与职业扩展架构

### 5.1 内容拆分

【重构＋新增】职业不是一套写死的 QWER，而是以下内容的组合：

- `ClassDefinition`：职业职能、基础成长、资源规则、默认能力集合和战术标签。
- `WeaponDefinition`：武器动作、基础伤害、射程、动作集与可用职业约束。
- `AbilityDefinition`：职业技能或角色专属能力，包含目标方式、消耗、冷却、施法时间和效果列表。
- `EffectDefinition`：伤害、治疗、护盾、位移、状态、生成、区域等可组合效果。
- `StatusDefinition`：持续时间、叠加、刷新、免疫、移除和优先级规则。
- `PassiveModifierDefinition`：属性或规则修正，不直接操作场景对象。
- `AnimSet` / Animator Override：表现替换，不承担玩法伤害。

职业技能、武器动作、角色专属能力和被动修正分开配置，避免“换武器等于换职业”或“新增职业复制整个控制器”。

### 5.2 技能执行管线

```text
Request → Validate → Reserve Cost → Windup / Targeting
→ Effect Schedule → Resolve → Cooldown / Recovery → Feedback Events
```

`AbilityContext` 至少包含施法者 ID、目标 ID 集合、楼层、位置、方向、动作 ID、随机种子和逻辑时间。效果只依赖能力接口，如 `IUnitQuery`、`IDamageTarget`、`IStatusReceiver`、`IMovementControl`、`ICombatStats`，不得直接调用 `SwordSwing`、`MonsterBrain`、具体面板或 `GameData`。

施法范围、目标类型和冷却属于技能本身，不再从“第一个效果的 `range`”推导。消耗和冷却的扣除时机、取消返还、死亡中断、重复施法和网络重试必须有统一规则。

### 5.3 伤害与状态结算

【保留＋重构】继续使用 `DamageInfo` 和统一生命入口，并冻结推荐顺序：

1. 校验来源、目标、楼层和存活状态；
2. 命中/破防/抗性等前置修正；
3. 护盾、减伤和部位倍率；
4. 扣除生命并生成结算结果；
5. 发布受击、状态、死亡或倒地事件；
6. 表现层消费结果。

普通伤害、技能、范围攻击和首领招式不得绕过统一入口。玩家“倒地”和彻底死亡应有独立状态，不再由多个组件各自推断。

【重构】受击闪色使用 `MaterialPropertyBlock` 或统一表现组件，不缓存并改写每个 Renderer 的运行时 `.material`，避免材质实例失控。

### 5.4 协同规则

【新增】队伍协同采用“事件—条件—效果”模型：例如某状态被施加、某类目标受击、救援完成等事件，经过队伍、距离、状态、冷却条件后触发有限效果。首期只支持可列出的条件与效果，不开发通用脚本语言。

必须明确：叠加上限、同类效果优先级、同时结算顺序、触发递归深度和冷却，防止无限连锁。协同设计以改变分工和空间决策为目标，不只做数值加成。

## 6. AI、普通敌人与首领架构

### 6.1 通用单位结构

```text
Perception（候选目标与可见性）
Decision（玩家指令 / 普通 AI / 首领动作选择）
Command Executor（移动、攻击、交互、施法）
Animation Driver（只反馈动作与速度）
```

【重构】`UnitBrain` 逐步变为指令执行与共用移动能力；`CharacterBrain` 只处理玩家指令优先级；普通怪物由感知和状态机驱动。决策不能直接修改 Renderer、UI 或奖励宝箱。

### 6.2 普通 AI

【重构＋新增】基础状态：巡逻/待机、警觉、追击、攻击、受控、返回、死亡；精英单位在此基础上增加动作和条件，不复制完整大脑。感知、目标选择、动作冷却与移动分离，并支持分帧更新。

### 6.3 首领遭遇

【重构】现有 `BossBrain` 拆为：

- `BossPhaseController`：阶段进入、退出、转换条件和一次性事件；
- `BossActionScheduler`：招式候选、冷却、距离/场地条件、打断和恢复；
- `EncounterDirector`：首领、召唤组、场地事件和任务节奏；
- `ArenaStateController`：可通行区域、危险区、机关和环境状态；
- `EncounterReward`：订阅遭遇完成，不由 Boss 自己找宝箱和发金币；
- `TelegraphController`：预警形状、时长、颜色和实际判定共用参数。

两类首领应分别验证“多行为主体与队伍分工”和“多部位/动态场地与阶段重构”，不能仅替换血量、伤害和红圈。阶段转换时必须处理进行中的招式、召唤物、预警、场地危险区和玩家交互状态，保证不会重复结算或留下不可清除的状态。

## 7. 场景、楼层与战争迷雾

### 7.1 场景划分

【新增】正式场景建议：

- `Boot`：应用服务、设置、内容索引和初始跳转；
- `Town`：整备、编队、成长和进入探索；
- `Floor_01`、`Floor_02`、`Floor_03`：三层主题化地牢；
- `Tests/`：战斗、交互、导航、迷雾、首领和联机隔离测试场景。

采用“应用场景常驻＋一个主要玩法场景”的简单加载策略。除非性能测试证明必要，不做多层同时常驻和复杂流式加载。跨层通过统一入口、出口和落点定义，不再由 `DungeonDoor` 硬编码传送对象与镜头根节点。

### 7.2 场景根层级模板

```text
[APP]                 仅应用/局内服务，按场景需要保留
[WORLD]
  Environment        模块、光照、碰撞、遮挡、NavMesh Surface
  LevelGraph         区域节点、连接、关键路径、可选路径
  Gameplay           出生点、遭遇、交互、撤离、楼层上下文
[ACTORS]             运行时生成单位，可用容器分组
[CAMERA]
[UI]
[DEBUG]              正式构建可关闭
```

场景只保存楼层静态内容和接线，不复制应用级管理器。每个场景必须通过“缺失服务、重复服务、空引用、错误层级”检查。

### 7.3 模块化关卡规范

【新增，数值待灰盒验证】以 1 Unity 单位 = 1 米；初始模块网格建议 2 米，主通道净宽 4～6 米，窄通道需专门做多单位通行测试。所有模块统一 Pivot、朝向、连接口和地面高度。

每个环境模块预制体包含：

- `Visual`：模型与材质；
- `Collision`：简化碰撞，不直接用复杂装饰网格；
- `Occlusion`：视线遮挡体，和视觉边界一致；
- `Navigation`：NavMesh 贡献、Modifier、Link 或 Obstacle；
- `Sockets`：门、转角、连接、灯光、装饰和玩法挂点；
- `Markers`：区域、地标、路径和调试信息。

区域图以有向图保存关键路径、可选路径、单向/双向连接、楼层衔接和撤离关系。区域图用于设计与验证，不代表运行时自动生成地图。

### 7.4 共享迷雾与显隐

【重构＋新增】每层拥有独立 `LevelContext` 和迷雾数据，可见状态分为：

- `Unexplored`：从未探索；
- `ExploredNotVisible`：有地形记忆，但当前不可见；
- `Visible`：当前任一友方视野可见。

所有单位共享同一套视野结果和遮挡规则；迷雾网格、敌人 Renderer、血条、小地图和联机同步使用同一感知服务的结果。不得由 `Visibility` 自行另算一套后直接冻结 AI——客户端不可见不等于房主停止模拟。

初版可用距离＋射线遮挡和低频网格更新，先保证正确性；只有 Profiler 证明必要时才扩大网格、提高频率或引入更复杂算法。跨层只保存当前设计要求的探索记忆，卸载楼层时明确序列化/丢弃策略。

## 8. 预制体生产规范

### 8.1 单位模板

```text
Unit_Base
  Identity / Registry Handle
  Health / Resource / Status / Combat Stats
  Navigation / Command Executor
  Interaction Runner
  VisualRoot
    Model
    Animator
    Sockets (Weapon, Muzzle, Hit, Overhead)
  Collision
    Hurtbox / Selection / Hit Queries
  UIAnchor
  Debug
```

【重构】公共能力放基础预制体，职业/敌人用 Variant 或组合子预制体；避免多层嵌套和在每个实例上重复改数值。Animator 位于模型子节点，不在根节点强制添加。逻辑代码可初始化时 `GetComponentInChildren<Animator>()`，但正式预制体应通过校验保证唯一有效 Animator。

### 8.2 单位变体

- `PlayerUnit_Base` → 各职业 Variant：数据、武器、技能集合、模型、Override。
- `EnemyUnit_Base` → 普通/精英 Variant：感知、动作集、数值和模型。
- `BossUnit_Base`：只包含公共单位能力；阶段与遭遇由独立组件/对象组合。
- `Projectile_Base`、`AreaEffect_Base`、`Telegraph_Base`、`PooledFX_Base`：统一生成、命中、归还和超时回收。

### 8.3 交互与环境预制体

`Interactable_Base` 只提供公共交互身份、碰撞与提示锚点；宝箱、救援目标、楼层入口、撤离点通过变体实现。环境模块不得把某一层专用的 Boss、奖励或 UI 引用打进共享基础预制体。

## 9. 材质、特效与光照规范

### 9.1 材质库

【重构】按用途建立少量母材质和明确变体：

- 角色：不透明 Lit，统一皮肤/装备纹理和受击表现；
- 环境：石材、木材、金属、地面等共享材质，主题层通过纹理与参数变体区分；
- 特效：Unlit/Particles，区分普通特效、预警、选中圈和迷雾；
- UI：图标、血条和地图专用，不与场景材质混用；
- Debug：线框、命中范围和导航显示，不进入正式表现。

禁止在 Boss 代码中临时 `new Material()` 作为长期方案；预警圈使用预制体与共享材质。需要逐单位变化时使用属性块或受控实例，并记录释放责任。

### 9.2 特效与预警

预警形状、持续时间、范围与实际判定读取同一动作参数；视觉只是解释机制，不允许“红圈大小和伤害范围各调各的”。所有短生命周期抛射物、爆炸、飘字、范围提示和拖尾定义 `OnRent/OnReturn` 重置清单，包括计时器、事件订阅、Trail、目标引用和缩放。

### 9.3 光照

每层使用独立光照配置和 Volume Profile，但共享曝光、色调和可读性基准。先保障敌我、预警、交互与迷雾下的辨识度，再增加氛围效果。迁移后必须对比 URP 材质、阴影、后处理和透明排序截图。

## 10. 数据资产与存档规范

### 10.1 数据分类

| 类型 | 保存形式 | 示例 | 禁止事项 |
|---|---|---|---|
| 内容定义 | ScriptableObject | 职业、单位、技能、武器、状态、楼层、遭遇 | 不写局内 HP、当前冷却和场景对象 |
| 场景配置 | Scene / Prefab | 模块位置、出生点、区域连接、光照 | 不把本可共享的平衡数值逐实例复制 |
| 用户设置 | JSON/PlayerPrefs（按用途） | 音量、按键、画质 | 不与存档混合 |
| 局外存档 | 带版本 JSON | 队伍、成长、解锁、仓库 | 不保存 Unity 对象引用和运行时 Transform |
| 局内运行状态 | 内存对象 | 血量、冷却、AI、当前迷雾 | 不反写内容资产 |

### 10.2 稳定 ID

每类内容有稳定字符串 ID，如 `class.xxx`、`ability.xxx`、`level.floor_01`。Unity GUID 负责资产引用，内容 ID 负责存档、网络和日志；二者不能互相替代。ID 创建后不复用、不随显示名修改，内容索引工具检查重复和缺失。

### 10.3 数据校验

【新增】编辑器和启动时检查：空引用、重复 ID、非法数值、技能效果缺失、职业动作集不匹配、动画状态缺失、楼层入口/出口不成对、撤离点无落点、网络预制体未登记等。错误应阻止正式构建或给出明确失败，不允许静默回退成敌队或默认数值。

## 11. Animator Controller 与动画数据规范

### 11.1 已冻结规则

1. 玩家全员单层，弃用 UpperBody；不恢复旧上下体分层方案。
2. 普攻采用 `Attack_Draw → Attack_Release`；代码只设置触发器，不主动 `Play()` 硬切。
3. `PlayerBase.controller` 为公共图，各角色用 Override；`Skeleton.controller` 供同构骷髅共用。
4. Any State 只用于受击和死亡等确需全局打断的状态，关闭 Can Transition To Self；**技能槽自 2026-11-05 起为例外**（允许 `AnyState → 槽`），见 `Docs/Decisions/ADR-0003_技能动画槽位化与子状态机.md` 与本文 §1.4。
5. `Animator Culling Mode = Always Animate`；导航单位默认不使用 Root Motion 驱动位移。
6. 命中使用动画状态 `normalizedTime` 比例窗口，读取失败回退代码时钟；AnimationEvent 不是主命中路径。
7. `UnitStats.attackSpeed` 为攻速单一来源，动画速度与执行器时长/冷却同步。

### 11.2 玩家公共状态

现有基础包括 `Locomotion`、`Attack_Draw`、`Attack_Release`、`Skill`、`Bash`、`Interact`、`Hit_A`、`Downed`、`Rise`。后续新增职业优先复用状态语义；只有确有新动作机制时才扩展公共图，避免把 `Fireball_Q`、`Assassin_E` 等内容名做成全局状态。

公共参数保持 `SpeedX/SpeedZ/Grounded/AttackSpeed` 与受控触发器。废弃参数如 `Jump` 在确认无引用后清理，不由 AI 擅自删除仍被场景或代码使用的条目。

### 11.3 动作时序资产

【新增】每个攻击动作配置：状态名、动画总时长、命中窗口起止、冷却、攻速缩放、是否可移动、取消窗口和回退时长。执行器按动作 ID 读取，不再在多个组件上分别维护互相矛盾的秒数。

动画替换验收必须包含：待机/移动、Draw/Release、技能、受击、中断、倒地、救援、复活和攻速变化；屏外与迷雾切换后动画时钟仍可读取。

## 12. 官方包与工具选型

版本号不提前写死为未经实测的组合。迁移时使用 Unity 6.3 Package Manager 推荐兼容版本，验证后锁定 `manifest.json` 与 `packages-lock.json`。

| 包 | 用途 | 决策 |
|---|---|---|
| URP / Shader Graph | 渲染与材质 | 必用，迁移重点回归 |
| AI Navigation | NavMesh Surface、Agent、Link、Obstacle | 必用，验证烘焙与多层落点 |
| Input System | 统一输入动作 | 必用目标；现有旧 Input 调用逐步迁移，不两套长期并存 |
| Cinemachine 3.x | 镜头 | 目标选型；2.x→3.x 有 API 和数据破坏，先备份再用升级器并检查引用 |
| Animation Rigging | 必要的骨骼辅助 | 保留评估；没有实际需求不扩大使用 |
| Test Framework | EditMode/PlayMode 测试 | 必用 |
| Netcode for GameObjects 2.x | 房主权威联机 | 新增；Unity 6.3 已弃用 1.x，不采用旧教程直接落地 |
| Unity Transport | NGO 传输 | 随兼容组合使用 |
| Multiplayer Tools / Multiplayer Play Mode | 联机分析与本机多端测试 | 推荐，版本兼容验证后使用 |
| Unity Behavior | 可视化行为图 | 【待验证】先用一个精英敌人和一个首领动作做试点；若图与代码双轨维护成本过高，则使用轻量 C# 行为树，不强制引入 |
| Timeline | 过场或阶段性演出 | 可选，不让演出成为关键结算的唯一驱动 |
| TextMeshPro / uGUI | HUD 与面板 | 沿用，不为本项目重做 UI 框架 |

不引入 DOTS/ECS、热更框架、程序生成地牢插件、大型通用 RPG 框架和来源不明的“全能战斗插件”。第三方素材与插件需记录许可证和来源。

## 13. 联机边界

【新增】目标为 Host 模式、房主权威、2～4 人 P2P，不使用专用服务器。

- 客户端发送选择、移动、攻击、施法、交互和撤离等指令；房主校验并裁决。
- 房主维护伤害、状态、掉落、救援、阶段、撤离和场景状态；客户端表现预测只限明确允许的少数项目。
- 所有网络对象有稳定生成与注销流程；职业、技能、物品和楼层用内容 ID，不传 Unity 资产引用。
- 迷雾共享结果、敌人显隐和 AI 模拟权威分离：不可见客户端可以隐藏表现，但房主逻辑不能停。
- 单机模式也走同一指令入口，避免后期为每个玩法函数再包一层 RPC。
- 联机测试覆盖重复指令、目标已死亡、交互竞争、跨层、断线、房主退出和重开；不承诺 NAT 全环境穿透，实际连接方案与测试网络条件需单独记录。

## 14. 测试、性能与验收门槛

### 14.1 自动测试

- EditMode：伤害顺序、状态叠加、冷却、资源、ID、存档迁移、区域图连通性。
- PlayMode：移动/攻击/交互、动画窗口回退、池归还、倒地救援、首领阶段、跨层与撤离。
- 网络测试：多端指令、权威结算、重复 RPC、并发交互和断线。
- 内容校验：所有正式场景、预制体、动画控制器和数据资产通过对应检查器。
- 分层、套件契约、断言 ID 规范与证据 schema：见 `Docs/06_测试架构与验收分层.md`。

### 14.2 性能原则

先测量再优化。重点观察逐帧全场扫描、GC、材质实例、NavMesh 高频重设目的地、迷雾网格更新、透明特效和多端消息量。对象池必须有回收正确性测试，不以“池里对象很多”作为性能完成证明。

### 14.3 研究评价数据

统一记录路线时间、无效折返、地标识别、路径选择、战斗时长、资源损耗、倒地频率、撤离率和新增职业修改范围。日志带版本、楼层、队伍配置和随机种子，避免只保存无法复现的结论。

## 15. 明确暂缓项

- DOTS/ECS、深度学习、神经网络和 TensorFlow；
- 程序生成地牢、攻城战、原创元素交互系统；
- 专用服务器、大型 MMORPG 式服务架构；
- 自研通用可视化脚本语言、通用行为树编辑器、热更和资源商店；
- 无实际性能证据的复杂流式加载、全局空间分区和渲染优化；
- 为每个职业、怪物或楼层复制独立流程、UI 和网络代码。

## 16. 推荐落地顺序

1. 完成 Unity 6.3 独立迁移基线和现有玩法回归；
2. 验收当前救援与通用动画机，冻结不再回退的规则；
3. 建立单位注册、楼层上下文、交互契约和池化归还契约；
4. 解耦技能上下文与职业执行器，做一个第四职业扩展测试；
5. 建立场景模板、模块规范、区域图和三层灰盒；
6. 重构共享感知，再制作普通/精英敌人和两类首领；
7. 打通整备—探索—搜集—撤离—成长闭环；
8. 以已稳定指令和状态接入完整 2～4 人联机；
9. 执行功能、性能、玩法和联机测试，保留研究数据；
10. 最后整理论文与演示，不在末期同时大改核心架构。
